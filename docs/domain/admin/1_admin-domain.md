# 관리자(Admin) 도메인 — 마스터 기획서 (이슈 #72)

> 관련 이슈: [#72 ADMIN 권한 범위 도메인 전체 명세 + 기획서/API 명세 role 컬럼 추가](https://github.com/GBSW-ReMake/GONE-server-V1/issues/72)
>
> **산출물 범위**: 이 문서는 기획서까지다. 실제 구현(엔티티/마이그레이션/엔드포인트)은
> 아래 "후속 이슈 목록" 절에 정리한 대로 도메인별 이슈로 나눠 진행한다 — 이 이슈 하나에서
> 전부 구현하지 않는다.

## 개요/목적
웹 어드민 페이지를 실제로 만들기 전에, "ADMIN이 정확히 무엇을 할 수 있는가"를 도메인을
가로질러 한 번에 정리한다.

지금까지 이 프로젝트는 "ADMIN은 모든 도메인에서 항상 전체 접근 가능"이라는 문장을
`docs/domain/outing/1_outing-domain.md`(권한 모델 절)에 프로젝트 공통 전제로만 적어두고,
각 도메인 기획서는 ADMIN 관련 설계를 "나중에 별도 웹 관리자 페이지에서"라며 계속
미뤄왔다(`35-user-deleted-filter.md`의 상태 변경 화면, `1_conduct-domain.md`의 카테고리
CRUD, `1_schoolcamp-domain.md`의 세션 취소/삭제 등). **그 결과 이 프로젝트 코드 전체를
뒤져도 `@PreAuthorize`에 `ADMIN`을 실제로 명시한 곳이 단 한 곳도 없다** — `outing`의
`@PreAuthorize` 5곳도 전부 `TEACHER`/`STUDENT`뿐이다. "ADMIN 전체 접근"은 지금까지 코드로
강제된 적이 없는, 문서상의 약속일 뿐이다.

이 문서는 그 공백을 다음 세 가지로 채운다.
1. 도메인별로 ADMIN이 실제로 조회/수정/삭제할 수 있어야 하는 것을 구체적인 기능 단위로
   추린다 — 웹 어드민 팀이 이 문서만 보고 화면 목록을 뽑을 수 있는 수준으로. 모든 어드민
   기능은 신규 `admin` 패키지가 전담한다(도메인별로 흩어놓지 않는다 — 아래 "정책" 참고).
2. 지금까지 없던 **운영 관점의 기능**을 신규로 정의한다 — (1) 시스템 전체 데이터 변경
   감사 로그, (2) Loki/Grafana 기반 애플리케이션 로그 열람.
3. 각 도메인 마스터 기획서의 엔드포인트 권한 표기를 표준화하는 후속 작업을 정의한다.

## 정책 (확정)
- **ADMIN 전체 접근을 "문서상 전제"에서 "코드로 강제되는 규칙"으로 승격한다.** 모든 어드민
  엔드포인트를 `/api/v1/admin/**` 경로 하나로 모으고, `SecurityConfig`에
  `.requestMatchers("/api/v1/admin/**").hasRole("ADMIN")` 규칙 한 줄을 추가해 **경로
  레벨에서 원천 차단**한다 — 엔드포인트마다 `@PreAuthorize`를 붙이는 걸 개별적으로 챙기는
  방식(빠뜨리기 쉽다)이 아니라, 구조적으로 "이 프리픽스 아래는 전부 ADMIN"을 강제하는
  방식을 택한다.
- **어드민 기능은 도메인별로 흩어놓지 않고 신규 `admin` 패키지가 전담한다.** 예: User 상태
  변경은 `AdminUserController`/`AdminUserService`(`admin` 패키지)가 담당하되, 내부적으로
  `user` 패키지의 `UserRepository`/`User` 엔티티를 그대로 의존성으로 가져와 쓴다 — 도메인의
  엔티티/리포지토리(데이터 소유권)는 원래 패키지에 그대로 두고, 그 위에서 동작하는
  "어드민 관점의 조회/수정/삭제 API"만 `admin` 패키지로 모은다. 이렇게 하면 (1) 위의
  경로 기반 보안 규칙이 정확히 이 패키지 하나와 대응해 일관되고, (2) 웹 어드민이 호출할
  API 전체를 `admin` 패키지 하나만 보고 파악할 수 있다.
- **감사 로그는 "시스템 전체의 데이터 변경 행위"를 기록한다** — 관리자 행위로 좁히지
  않는다. 다만 대상은 **데이터를 변경하는 행위**로 한정한다(로그인/조회 등 비변경 행위는
  대상이 아니다 — 그것까지 포함하면 사실상 전체 요청 로깅이 되어 "무엇이 왜 바뀌었는지
  추적"이라는 감사 로그 본연의 목적이 흐려진다). 로그인 성공/실패 같은 보안 이벤트는
  범위가 다른 별도 주제라 이 문서에서 다루지 않는다(필요하면 별도 이슈).
- **애플리케이션 로그는 Loki + Grafana를 `docker-compose.dev.yml`에 자체 호스팅으로
  추가한다.** 외부 SaaS/클라우드 로그 서비스에 종속되지 않고, 지금 EC2 인스턴스 안에서
  컨테이너로 해결한다.
- **역할 표기 표준화는 이 이슈에서 직접 각 마스터 기획서를 고치지 않는다.** 표준 형식만
  이 문서에서 정의하고, 실제 반영은 별도 문서 전용 이슈로 분리한다(아래 "후속 이슈 목록").

## 권한 모델
- 역할 코드 전체(`V6__add_role_and_user_role.sql` + `V10__add_user_status.sql`):
  `STUDENT`, `TEACHER`, `ADMIN`, `STUDENT_COUNCIL`, `DISCIPLINE`, `GENERAL_AFFAIRS`,
  `ENVIRONMENT`, `BROADCASTING`, `ATHLETICS`, `GRADUATE` (10개).
- `ADMIN`은 이 문서가 다루는 모든 신규/기존 엔드포인트에 예외 없이 접근 가능하다 — 아래
  "도메인별 어드민 기능 목록"의 각 항목은 전부 `ADMIN` 전용이거나 `ADMIN`을 포함한다.
- 감사 로그/애플리케이션 로그 열람은 **`ADMIN`만** 접근 가능하다(다른 역할은 포함하지
  않는다 — `DISCIPLINE`/`TEACHER` 등 기존에 일부 상위 권한을 가진 역할도 이 두 기능에는
  접근할 수 없다. 운영 정보이지 학교 업무 정보가 아니기 때문).

## 도메인별 어드민 기능 목록
각 행은 "웹 어드민 화면 하나"에 대응할 수 있는 단위로 정리했다. 전부 `admin` 패키지에
구현되고 경로는 `/api/v1/admin/{도메인}/...` 형태를 따른다. `상태` 열은 구현 여부다.

| 도메인 | 기능 | 방식 | 상태 |
|---|---|---|---|
| User | 전체 사용자 목록 조회(검색/페이지네이션) | `AdminUserController` 신규, `UserRepository` 재사용 | 미구현 |
| User | 상태 변경(`ACTIVE`↔`GRADUATED`↔`WITHDRAWN`) | `AdminUserController` 신규, `#35`의 `status` 컬럼 재사용 | 미구현 |
| User | 역할(Role) 부여/변경 | `#15`가 별도로 이미 다루는 중 — 이 문서에서 새로 설계하지 않음(다만 최종 위치는 `#15` 쪽에서 이 문서의 `admin` 패키지 정책에 맞춰 재검토 필요) | `#15` 진행 중 |
| Gbsw | 명단 개별 조회/수정/삭제 | `AdminGbswController` 신규(현재는 엑셀 일괄 임포트만 존재), `GbswRepository` 재사용 | 미구현 |
| Outing | 전체 외출증 목록/상세 조회(소유권 무관, 상태·기간 필터) | `AdminOutingController` 신규, `OutingRepository` 재사용 | 미구현 |
| Outing | 상태 강제 변경/취소 | **설계하지 않음** — 아래 리스크 참고 | 대상 아님 |
| Notification | 발송 이력 전체 열람(사용자 문의 대응용) | `AdminNotificationController` 신규, `NotificationRepository` 재사용 | 미구현 |
| Conduct(미구현 도메인) | 정정/취소 | 이미 `1_conduct-domain.md`가 소유권 무관 `ADMIN` 권한으로 설계 완료(`conduct` 패키지 자체 컨트롤러 — 이 항목은 `admin` 패키지로 옮기지 않는다, 아래 참고) | 도메인 자체가 미구현(`#58`) |
| Conduct(미구현 도메인) | 카테고리 CRUD | 이미 `1_conduct-domain.md`가 "별도 웹 관리자 페이지" 몫으로 명시 — `AdminConductController` 신규 | `#58` 후속 |
| SchoolCamp(미구현 도메인) | 세션 등록 | 이미 `1_schoolcamp-domain.md`가 관리자 몫으로 설계(`schoolcamp` 패키지 자체 컨트롤러) | `#38` 진행 중 |
| SchoolCamp(미구현 도메인) | 세션 취소/삭제(신청자 존재 시 처리 포함) | `1_schoolcamp-domain.md`가 범위 밖으로 명시 — `AdminSchoolCampController` 신규, 정책은 후속 이슈에서 확정 | `#38` 후속 |

**"조회/수정/삭제"와 "그 도메인 본연의 업무 기능"을 구분한다**: Conduct의 정정/취소,
SchoolCamp의 세션 등록처럼 **원래부터 그 도메인 엔드포인트 자체에 `ADMIN`이 포함되도록
설계된 기능**은 `admin` 패키지로 옮기지 않는다 — 그 기능은 애초에 ADMIN 전용이 아니라
TEACHER/DISCIPLINE 등도 함께 쓰는 일반 업무 엔드포인트이기 때문이다. `admin` 패키지가
전담하는 건 **"ADMIN만 쓰는" 조회/수정/삭제**(전체 목록 조회, 상태 강제 변경, 카테고리
CRUD 등)로 한정한다.

**Outing 상태 강제 변경을 설계하지 않는 이유**: `Outing` 레코드는 설계상 영구 보존되고
(`OutingStatus` 전이만 있고 하드 삭제 없음), 상태 전이는 이미 승인/거절/출발/도착 각
엔드포인트가 감사 가능한 방식으로 처리한다. ADMIN이 상태를 임의로 되돌리는 기능을 추가하면
오히려 "누가 언제 실제로 승인/거절했는지"를 흐리게 만들어 이 도메인이 원래 지키려던 감사
추적성을 해친다. 필요해지면(예: 명백한 오조작 정정) 그때 감사 로그와 함께 별도로 설계한다.

## 신규 도메인: 시스템 전체 감사 로그 (`audit_log`)
관리자 행위만이 아니라 **시스템 전체에서 일어나는 데이터 변경 행위**를 기록한다(범위 정의는
위 "정책" 절 참고 — 변경 행위만 대상, 로그인 등 비변경 이벤트는 제외).

### `AuditLog` 엔티티 (신규, `admin` 패키지 — 감사 로그는 ADMIN만 조회하므로 데이터
소유권은 `admin`이 갖는다)
- `id` (PK)
- `actorUserId` — 행위를 수행한 사용자 `User.id` (FK, ADMIN이 아닌 일반 사용자의 행위도
  포함하므로 "관리자"로 이름 붙이지 않는다)
- `action` — 행위 코드(예: `OUTING_REQUEST`, `OUTING_APPROVE`, `USER_STATUS_CHANGE`,
  `CONDUCT_RECORD_CREATE`). 전체 목록은 여기서 미리 확정하지 않는다 — 각 후속 이슈가
  자신의 도메인에 `@Audited` 어노테이션을 붙이면서 필요한 action 값을 그 이슈 기획서에
  추가한다.
- `targetDomain` — 대상 도메인명(예: `user`, `outing`, `conduct`)
- `targetId` — 대상 레코드 PK
- `detail` — 변경 전/후 값 등 자유 형식 텍스트(JSON 문자열로 저장, `TEXT` 컬럼 — 이
  프로젝트에 JSON 컬럼 타입 선례가 없어 새로 도입하지 않고 `TEXT`로 저장 후 애플리케이션이
  파싱)
- `createdAt`

### 기록 방식 — AOP 기반 `@Audited` 어노테이션 (신규 패턴, 도입 근거 명시)
이 프로젝트에 AOP(`@Aspect`) 선례가 없었지만, "시스템 전체" 감사라는 요구를 만족하려면
변경 지점마다 로그 기록을 수동으로 호출하는 방식은 호출 누락 위험이 너무 커서 현실적이지
않다 — 이게 AOP를 새로 도입하는 근거다(code-style.md "새 패턴이 정말 필요하면 근거를
남기고 추가한다"에 해당).
- `@Audited(action = "...", targetDomain = "...")` 어노테이션(신규, `common/audit` 패키지 —
  `common/redis`/`common/exception`처럼 도메인 횡단 인프라가 모이는 자리)을 감사 대상
  서비스 메서드에 붙인다.
- `AuditAspect`(`@Aspect`, `@AfterReturning`, `common/audit` 패키지)가 이 어노테이션이 붙은
  메서드가 **성공적으로 리턴한 직후** `actorUserId`(`SecurityContext`에서 추출),
  `targetId`(메서드 반환값 또는 인자에서 관례적으로 추출 — 정확한 추출 규칙은 구현 이슈에서
  확정), `detail`을 채워 `AuditLogRepository`(`admin` 패키지)에 저장한다.
- 대상 메서드가 `@Transactional`이면 어드바이스도 같은 트랜잭션 안에서 실행되므로, 원래
  행위가 롤백되면 감사 로그도 함께 롤백된다 — "실제로 일어나지 않은 일이 감사 로그에는
  남는" 불일치가 구조적으로 발생하지 않는다.
- 각 후속 이슈가 자신의 도메인에서 감사 대상 메서드에 `@Audited`를 붙이는 작업까지
  담당한다(이 이슈에서 전체 도메인에 일괄 적용하지 않는다).

### 조회 엔드포인트
- `GET /api/v1/admin/audit-logs?actorUserId=&targetDomain=&from=&to=` — 조건별 감사 로그
  목록 조회, `ADMIN` 전용. 상세 요청/응답 스키마는 이 엔드포인트를 실제로 구현하는 후속
  이슈에서 확정한다(이 문서는 존재/권한/대략적인 필터만 못박는다).

## 신규 도메인: 애플리케이션 로그 열람 (Loki + Grafana, 자체 호스팅)
### 인프라 구성 (`deploy/docker-compose.dev.yml`에 신규 서비스 추가)
- **Loki**: 로그 저장/색인. `app` 컨테이너와 같은 compose 스택에 신규 서비스로 추가.
- **Promtail**(또는 Grafana Alloy): `app` 컨테이너의 로그를 읽어 Loki로 전송하는 에이전트.
  Spring Boot 쪽은 표준 `logging.file.name` 설정으로 EC2 볼륨에 로그 파일을 남기고,
  Promtail이 그 파일을 tail해서 Loki로 보낸다.
- **Grafana**: Loki를 데이터소스로 붙여 대시보드/탐색 UI 제공. 운영자가 직접 깊은 디버깅을
  할 때는 Grafana UI에 직접 접속(내부망/SSH 터널 전제, 별도 인증 체계 — 이 프로젝트의
  JWT 인증과는 분리된 별개 로그인)해서 쓴다.
- 신규 컨테이너 3개(Loki/Promtail/Grafana)가 추가되므로, 현재 dev EC2 인스턴스의
  메모리/디스크 여유가 충분한지 반드시 먼저 확인해야 한다 — 구현 이슈의 사전 준비(0단계)
  항목으로 남긴다.

### 웹 어드민 연동 — 백엔드 프록시 방식
웹 어드민 프론트엔드가 Grafana에 별도 로그인하지 않고 이 프로젝트의 기존 JWT
인증/`ApiResponse<T>` 컨벤션 그대로 로그를 볼 수 있도록, 백엔드가 Loki의 쿼리 API를
프록시한다(API 설계 6원칙 "직관적 일관성"과 맞물림).
- `GET /api/v1/admin/logs?level=&keyword=&from=&to=` — 백엔드가 이 요청을 Loki의
  `/loki/api/v1/query_range`로 변환해 호출하고, 결과를 이 프로젝트의 응답 포맷으로 감싸
  반환한다. `ADMIN` 전용. 실시간 스트리밍(WebSocket 등)은 이번 범위가 아니다(폴링 기반
  조회로 시작 — 운영 중 필요성이 확인되면 재검토).
- 상세 요청/응답 스키마, Loki 쿼리 변환 로직은 이 엔드포인트를 실제로 구현하는 후속
  이슈에서 확정한다.

## 역할(권한) 표기 표준화
연구 결과, 각 마스터 기획서는 엔드포인트마다 마크다운 표가 아니라
`**권한**: {역할}` 한 줄로 권한을 표기하고 있다(예: `1_outing-domain.md:209`). 표준 형식을
다음과 같이 정의한다.
- 각 엔드포인트 섹션의 `**권한**:` 줄은 `ADMIN`을 별도로 나열하지 않는다(위 "권한 모델"
  절의 전제로 이미 포함되므로 매 줄 반복 표기하지 않는다 — 대신 각 마스터 기획서 최상단에
  "이 문서의 모든 엔드포인트는 `ADMIN`을 항상 포함한다"는 안내 문구 한 줄을 추가한다).
- 각 마스터 기획서 최상단(개요/목적 다음)에 "엔드포인트 요약 표"(Method+Path / 권한 / 설명
  3컬럼)를 신설한다 — 지금까지 어떤 마스터 기획서에도 이런 요약 표가 없었다(전부 프로즈로만
  나열).
- Notion API 명세서에도 각 엔드포인트 항목에 "역할" 필드를 추가한다.
- **이 표준화 작업 자체는 코드 변경이 없는 순수 문서 작업**이라 도메인별로 쪼개지 않고 문서
  전용 이슈 하나로 처리한다(아래 후속 이슈 목록).

## API 설계 6원칙 체크
- **한 가지를 잘하기**: 위 후속 이슈 목록이 이미 도메인/기능 단위로 쪼개져 있어 각 이슈가
  엔드포인트 1~2개 범위를 넘지 않는다.
- **빠르게 시작**: 이 마스터 문서는 요청/응답 JSON을 확정하지 않는다 — 각 후속 이슈가
  구현 시점에 원칙 2(요청/응답 예시 필수)를 지킨다. 이 문서 자체는 "무엇을 만들지"의
  스코프 문서이지 최종 API 스펙이 아니다(api-design.md "마스터 기획서 재검토" 절과 같은
  성격 — 스냅샷).
- **직관적 일관성**: 신규 어드민 엔드포인트 전부 `/api/v1/admin/{도메인}` 경로(기존
  `/api/v1/{도메인}`과 구분되는 별도 프리픽스 — 보안 규칙을 경로 하나로 강제하기 위한
  의도적 선택), `ApiResponse<T>`, `{DOMAIN}_NNN` 에러 코드 컨벤션을 그대로 따른다.
  로그 조회 엔드포인트만 예외적으로 외부 시스템(Loki)을 프록시하지만, 응답 포맷은 동일하게
  `ApiResponse<T>`로 감싼다.
- **의미 있는 오류**: 각 후속 이슈가 자신의 `{Domain}ErrorCode`에 필요한 코드를 추가한다.
  `admin` 패키지 자체도 `AdminErrorCode`가 필요해지면 그때 추가한다(현재 이 문서 범위에서
  확정할 에러 케이스 없음). 로그 조회 프록시는 Loki 쿼리 실패를 `500`으로 뭉개지 않고
  구분되는 에러 코드로 매핑해야 한다 — 후속 이슈에서 확정.
- **확장성/성능**: 감사 로그·애플리케이션 로그·User/Gbsw 전체 목록 조회는 전부 컬렉션
  응답이므로, 각 후속 이슈에서 페이지네이션 여부를 반드시 결정한다(이 문서에서는 미리
  확정하지 않음 — 데이터 규모를 아는 구현 시점에 결정하는 게 더 정확하다).
- **하위 호환성**: 전부 신규 엔드포인트라 기존 응답을 깨지 않는다.

## 리스크 및 고려사항
- **`admin` 패키지가 여러 도메인의 리포지토리/엔티티에 의존하는 구조적 결합**: 의도한
  설계이지만(위 "정책" 참고), 도메인 쪽에서 엔티티/리포지토리 시그니처를 바꾸면 `admin`
  패키지가 함께 깨질 수 있다는 뜻이기도 하다 — 각 도메인의 후속 변경 시 `admin` 패키지
  영향 여부를 코드 리뷰에서 확인해야 한다.
- **감사 로그 커버리지는 여전히 "누가 `@Audited`를 붙였는가"에 의존한다**: AOP로
  기록 누락(호출을 깜빡하는 것) 자체는 구조적으로 없앴지만, 새 변경 메서드를 만들 때
  `@Audited`를 붙이는 걸 잊으면 그 행위는 감사 대상에서 빠진다 — 각 후속 이슈의 코드
  리뷰(9단계)에서 "이 변경이 감사 로그 대상인지" 체크리스트 항목으로 명시적으로 확인해야
  한다(수동 호출보다는 훨씬 안전하지만 완전히 자동은 아니다).
- **Loki/Promtail/Grafana 컨테이너 3개 추가로 인한 EC2 리소스 증가**: 현재 인스턴스가
  MySQL/Redis/App/Nginx만으로 이미 얼마나 여유가 있는지 확인이 안 됐다 — 구현 이슈 착수
  전 리소스 여유를 먼저 점검해야 한다(부족하면 인스턴스 업사이즈 필요, 별도 비용 발생).
- **로그 보존 기간/디스크 사용량**: Loki도 결국 EC2 로컬 볼륨에 데이터를 쌓으므로,
  보존 기간(retention) 정책을 정하지 않으면 디스크가 무한정 찬다 — 구현 이슈에서 반드시
  retention 설정을 포함해야 한다.
- **ADMIN 전체 접근이 지금까지 코드로 강제된 적이 없었다는 사실 자체가 기존 보안 공백**이다
  — 이 문서 이전에는 ADMIN 역할을 가진 계정이 있어도 그 역할이 실제로 어떤 특별한 접근을
  부여하는지 코드 어디에도 없었다(일반 인증 사용자와 동일). `admin` 패키지 기반 구조 +
  경로 레벨 보안 설정 이슈가 실제로 머지되기 전까지 이 공백은 유지된다.
- **Conduct/SchoolCamp는 도메인 자체가 아직 없다**: 이 문서가 정의한 그 두 도메인의 어드민
  기능은 코드가 하나도 없는 상태에서의 설계이므로, 실제 도메인 구현(`#58`/`#38`)이 먼저
  끝나야 착수할 수 있다 — 순서를 반드시 지킨다.
- **감사 로그 `detail` 컬럼(TEXT/JSON 문자열)**: 스키마가 없는 자유 형식이라 검색/필터가
  제한적이다. 나중에 검색 요구가 커지면 주요 필드를 별도 컬럼으로 분리하는 마이그레이션이
  필요할 수 있다 — 지금은 "무엇이 바뀌었는지 기록"이 목적이라 충분하다고 판단.
- **Grafana 직접 접속은 이 프로젝트의 JWT 인증 체계와 별개의 로그인**이다 — 운영자 전용
  통로이므로 계정 관리(초기 비밀번호, 접근 IP 제한 등)를 구현 이슈에서 함께 정해야 한다.
