# 관리자(Admin) 도메인 — 마스터 기획서 (이슈 #72)

> 관련 이슈: [#72 ADMIN 권한 범위 도메인 전체 명세 + 기획서/API 명세 role 컬럼 추가](https://github.com/GBSW-ReMake/GONE-server-V1/issues/72)
>
> **산출물 범위**: 이 문서는 기획서까지다. 실제 구현(엔티티/마이그레이션/엔드포인트)은
> 아래 "후속 이슈 목록" 절에 정리한 대로 도메인별 이슈로 나눠 진행한다 — 이 이슈 하나에서
> 전부 구현하지 않는다.

## 개요/목적
웹 어드민 페이지를 실제로 만들기 전에, "ADMIN이 정확히 무엇을 할 수 있는가"를 도메인을
가로질러 한 번에 정리한다.

지금까지 이 프로젝트는 "ADMIN은 모든 도메인에서 항상 전체 접근 가능"이라는 문장을
`docs/domain/outing/1_outing-domain.md`(권한 모델 절)에 프로젝트 공통 전제로만 적어두고,
각 도메인 기획서는 ADMIN 관련 설계를 "나중에 별도 웹 관리자 페이지에서"라며 계속
미뤄왔다(`35-user-deleted-filter.md`의 상태 변경 화면, `1_conduct-domain.md`의 카테고리
CRUD, `1_schoolcamp-domain.md`의 세션 취소/삭제 등). **그 결과 이 프로젝트 코드 전체를
뒤져도 `@PreAuthorize`에 `ADMIN`을 실제로 명시한 곳이 단 한 곳도 없다** — `outing`의
`@PreAuthorize` 5곳도 전부 `TEACHER`/`STUDENT`뿐이다. "ADMIN 전체 접근"은 지금까지 코드로
강제된 적이 없는, 문서상의 약속일 뿐이다.

이 문서는 그 공백을 다음 세 가지로 채운다.
1. 도메인별로 ADMIN이 실제로 조회/수정/삭제할 수 있어야 하는 것을 구체적인 기능 단위로
   추린다 — 웹 어드민 팀이 이 문서만 보고 화면 목록을 뽑을 수 있는 수준으로.
2. 지금까지 없던 **운영 관점의 기능**(관리자 행위 감사 로그, 애플리케이션 로그 열람)을
   신규 도메인으로 정의한다.
3. 각 도메인 마스터 기획서의 엔드포인트 권한 표기를 표준화하는 후속 작업을 정의한다.

## 정책 (확정)
- **ADMIN 전체 접근을 "문서상 전제"에서 "코드로 강제되는 규칙"으로 승격한다.** 아래 후속
  이슈들이 실제 엔드포인트를 구현할 때는 반드시 `@PreAuthorize`에 `ADMIN`을 명시적으로
  포함시킨다(예: `@PreAuthorize("hasRole('TEACHER') or hasRole('ADMIN')")`) — "ADMIN은
  당연히 되겠지"라고 암묵적으로 남겨두지 않는다.
- **도메인 고유 어드민 기능은 그 도메인 패키지에 그대로 둔다.** 예: User 상태 변경은
  `user` 패키지, Gbsw 명단 CRUD는 `gbsw` 패키지에 구현한다. `admin` 패키지는 어느 도메인에도
  속하지 않는 **횡단 관심사**(감사 로그, 애플리케이션 로그 열람)만 담당한다 — "관리자가
  쓰는 기능이니 전부 admin 패키지로"라고 몰아넣지 않는다(code-style.md의 기존 도메인 패키지
  구조 원칙과 동일한 이유).
- **감사 로그는 "관리자가 수행한 변경 행위"만 기록한다.** 일반 사용자의 행위(외출 신청,
  상벌점 조회 등)는 대상이 아니다 — 대상을 넓히면 사실상 전체 요청 로깅이 되어 버려 이
  이슈의 "관리자 행위 추적"이라는 목적과 어긋난다.
- **애플리케이션 로그는 별도 로그 집계 서비스(Loki/CloudWatch 등) 없이, 이 프로젝트
  규모(단일 EC2, `docker-compose`)에 맞는 가장 단순한 방식으로 간다** — Spring Boot 표준
  파일 로깅(`logging.file.name`)으로 EC2 볼륨에 로그 파일을 남기고, ADMIN 전용 엔드포인트가
  그 파일의 최근 구간을 검색해 반환한다. 외부 로그 서비스 도입은 운영 규모가 실제로 커지면
  그때 별도 이슈로 재검토한다(YAGNI).
- **역할 표기 표준화는 이 이슈에서 직접 각 마스터 기획서를 고치지 않는다.** 표준 형식만
  이 문서에서 정의하고, 실제 반영은 별도 문서 전용 이슈로 분리한다(아래 "후속 이슈 목록").

## 권한 모델
- 역할 코드 전체(`V6__add_role_and_user_role.sql` + `V10__add_user_status.sql`):
  `STUDENT`, `TEACHER`, `ADMIN`, `STUDENT_COUNCIL`, `DISCIPLINE`, `GENERAL_AFFAIRS`,
  `ENVIRONMENT`, `BROADCASTING`, `ATHLETICS`, `GRADUATE` (10개).
- `ADMIN`은 이 문서가 다루는 모든 신규/기존 엔드포인트에 예외 없이 접근 가능하다 — 아래
  "도메인별 어드민 기능 목록"의 각 항목은 전부 `ADMIN` 전용이거나 `ADMIN`을 포함한다.
- 감사 로그/애플리케이션 로그 열람은 **`ADMIN`만** 접근 가능하다(다른 역할은 포함하지
  않는다 — `DISCIPLINE`/`TEACHER` 등 기존에 일부 상위 권한을 가진 역할도 이 두 기능에는
  접근할 수 없다. 운영 정보이지 학교 업무 정보가 아니기 때문).

## 도메인별 어드민 기능 목록
각 행은 "웹 어드민 화면 하나"에 대응할 수 있는 단위로 정리했다. `상태` 열은 구현 여부다.

| 도메인 | 기능 | 방식 | 상태 |
|---|---|---|---|
| User | 전체 사용자 목록 조회(검색/페이지네이션) | 신규 엔드포인트 | 미구현 |
| User | 상태 변경(`ACTIVE`↔`GRADUATED`↔`WITHDRAWN`) | 신규 엔드포인트, `#35`의 `status` 컬럼 재사용 | 미구현 |
| User | 역할(Role) 부여/변경 | `#15`가 별도로 이미 다루는 중 — 이 문서에서 새로 설계하지 않음 | `#15` 진행 중 |
| Gbsw | 명단 개별 조회/수정/삭제 | 신규 엔드포인트(현재는 엑셀 일괄 임포트만 존재) | 미구현 |
| Outing | 전체 외출증 목록/상세 조회(소유권 무관, 상태·기간 필터) | 신규 엔드포인트 | 미구현 |
| Outing | 상태 강제 변경/취소 | **설계하지 않음** — 아래 리스크 참고 | 대상 아님 |
| Notification | 발송 이력 전체 열람(사용자 문의 대응용) | 신규 엔드포인트 | 미구현 |
| Conduct(미구현 도메인) | 정정/취소 | 이미 `1_conduct-domain.md`가 소유권 무관 `ADMIN` 권한으로 설계 완료 | 도메인 자체가 미구현(`#58`) |
| Conduct(미구현 도메인) | 카테고리 CRUD | 이미 `1_conduct-domain.md`가 "별도 웹 관리자 페이지" 몫으로 명시 — 이 문서가 그 몫 | `#58` 후속 |
| SchoolCamp(미구현 도메인) | 세션 등록 | 이미 `1_schoolcamp-domain.md`가 관리자 몫으로 설계 | `#38` 진행 중 |
| SchoolCamp(미구현 도메인) | 세션 취소/삭제(신청자 존재 시 처리 포함) | `1_schoolcamp-domain.md`가 범위 밖으로 명시 — 이 문서가 그 몫, 정책은 후속 이슈에서 확정 | `#38` 후속 |

**Outing 상태 강제 변경을 설계하지 않는 이유**: `Outing` 레코드는 설계상 영구 보존되고
(`OutingStatus` 전이만 있고 하드 삭제 없음), 상태 전이는 이미 승인/거절/출발/도착 각
엔드포인트가 감사 가능한 방식으로 처리한다. ADMIN이 상태를 임의로 되돌리는 기능을 추가하면
오히려 "누가 언제 실제로 승인/거절했는지"를 흐리게 만들어 이 도메인이 원래 지키려던 감사
추적성을 해친다. 필요해지면(예: 명백한 오조작 정정) 그때 감사 로그와 함께 별도로 설계한다.

## 신규 도메인: 관리자 행위 감사 로그 (`admin_audit_log`)
### `AdminAuditLog` 엔티티 (신규, `admin` 패키지)
- `id` (PK)
- `actorUserId` — 행위를 수행한 관리자 `User.id` (FK)
- `action` — 행위 코드(예: `USER_STATUS_CHANGE`, `GBSW_UPDATE`, `CONDUCT_CATEGORY_DELETE`).
  각 후속 이슈가 자신의 도메인에 필요한 `action` 값을 그 이슈 기획서에서 추가로 정의한다
  (여기서 전체 목록을 미리 확정하지 않는다 — 후속 이슈가 실제로 어떤 변경 지점을 갖는지
  구현 시점에 더 정확히 알 수 있다).
- `targetDomain` — 대상 도메인명(예: `user`, `gbsw`)
- `targetId` — 대상 레코드 PK
- `detail` — 변경 전/후 값 등 자유 형식 텍스트(JSON 문자열로 저장, `TEXT` 컬럼 — 이
  프로젝트에 JSON 컬럼 타입 선례가 없어 새로 도입하지 않고 `TEXT`로 저장 후 애플리케이션이
  파싱)
- `createdAt`

### 기록 방식
- 이 프로젝트에 AOP(`@Aspect`) 선례가 없어, 새 패턴을 임의로 도입하지 않는다
  (code-style.md 원칙). 대신 각 어드민 전용 서비스 메서드가 변경 성공 직후
  `AdminAuditLogService.record(...)`를 명시적으로 호출하는 방식을 표준으로 삼는다 — 호출을
  빠뜨릴 여지는 있지만, 이 프로젝트 규모에서 AOP 인프라를 새로 들이는 비용보다 코드 리뷰로
  누락을 잡는 비용이 더 낮다고 판단(트레이드오프, 아래 리스크 참고).

### 조회 엔드포인트
- `GET /api/v1/admin/audit-logs?actorUserId=&targetDomain=&from=&to=` — 조건별 감사 로그
  목록 조회, `ADMIN` 전용. 상세 요청/응답 스키마는 이 엔드포인트를 실제로 구현하는 후속
  이슈에서 확정한다(이 문서는 존재/권한/대략적인 필터만 못박는다).

## 신규 도메인: 애플리케이션 로그 열람
- Spring Boot 표준 `logging.file.name` 설정으로 EC2 볼륨에 로그 파일을 남긴다(신규
  라이브러리/외부 서비스 도입 없음).
- `GET /api/v1/admin/logs?level=&keyword=&limit=` — 최근 로그 파일에서 레벨/키워드로 필터한
  구간을 반환, `ADMIN` 전용. 실시간 스트리밍은 이번 범위가 아니다(폴링 기반 조회로 충분 —
  운영 규모가 커지면 재검토).

## 역할(권한) 표기 표준화
연구 결과, 각 마스터 기획서는 엔드포인트마다 마크다운 표가 아니라
`**권한**: {역할}` 한 줄로 권한을 표기하고 있다(예: `1_outing-domain.md:209`). 표준 형식을
다음과 같이 정의한다.
- 각 엔드포인트 섹션의 `**권한**:` 줄은 `ADMIN`을 별도로 나열하지 않는다(위 "권한 모델"
  절의 전제로 이미 포함되므로 매 줄 반복 표기하지 않는다 — 대신 각 마스터 기획서 최상단에
  "이 문서의 모든 엔드포인트는 `ADMIN`을 항상 포함한다"는 안내 문구 한 줄을 추가한다).
- 각 마스터 기획서 최상단(개요/목적 다음)에 "엔드포인트 요약 표"(Method+Path / 권한 / 설명
  3컬럼)를 신설한다 — 지금까지 어떤 마스터 기획서에도 이런 요약 표가 없었다(전부 프로즈로만
  나열).
- Notion API 명세서에도 각 엔드포인트 항목에 "역할" 필드를 추가한다.
- **이 표준화 작업 자체는 코드 변경이 없는 순수 문서 작업**이라 도메인별로 쪼개지 않고 문서
  전용 이슈 하나로 처리한다(아래 후속 이슈 목록).

## API 설계 6원칙 체크
- **한 가지를 잘하기**: 위 후속 이슈 목록이 이미 도메인/기능 단위로 쪼개져 있어 각 이슈가
  엔드포인트 1~2개 범위를 넘지 않는다.
- **빠르게 시작**: 이 마스터 문서는 요청/응답 JSON을 확정하지 않는다 — 각 후속 이슈가
  구현 시점에 원칙 2(요청/응답 예시 필수)를 지킨다. 이 문서 자체는 "무엇을 만들지"의
  스코프 문서이지 최종 API 스펙이 아니다(api-design.md "마스터 기획서 재검토" 절과 같은
  성격 — 스냅샷).
- **직관적 일관성**: 신규 엔드포인트 전부 `/api/v1/{도메인}` 경로, `ApiResponse<T>`,
  `{DOMAIN}_NNN` 에러 코드 컨벤션을 그대로 따르는 것을 전제로 한다.
- **의미 있는 오류**: 각 후속 이슈가 자신의 `{Domain}ErrorCode`에 필요한 코드를 추가한다.
  `admin` 패키지 자체도 `AdminErrorCode`가 필요해지면 그때 추가한다(현재 이 문서 범위에서
  확정할 에러 케이스 없음).
- **확장성/성능**: 감사 로그·애플리케이션 로그·User/Gbsw 전체 목록 조회는 전부 컬렉션
  응답이므로, 각 후속 이슈에서 페이지네이션 여부를 반드시 결정한다(이 문서에서는 미리
  확정하지 않음 — 데이터 규모를 아는 구현 시점에 결정하는 게 더 정확하다).
- **하위 호환성**: 전부 신규 엔드포인트라 기존 응답을 깨지 않는다.

## 리스크 및 고려사항
- **감사 로그 기록 누락 위험**: AOP 없이 각 서비스 메서드가 명시적으로 기록을 호출하는
  방식은 새 어드민 기능을 추가할 때 기록 호출을 빠뜨릴 수 있다 — 각 후속 이슈의 코드
  리뷰(9단계)에서 "이 변경이 감사 로그 대상인지" 체크리스트 항목으로 명시적으로 확인해야
  한다.
- **애플리케이션 로그 파일이 EC2 로컬 디스크에만 남는다**: 컨테이너/인스턴스가 교체되면
  과거 로그가 유실된다(로그 로테이션도 별도 설정 필요). 운영 감사가 중요해지면 외부 저장소
  전송을 재검토해야 한다 — 지금은 규모상 감수하는 트레이드오프.
- **ADMIN 전체 접근이 지금까지 코드로 강제된 적이 없었다는 사실 자체가 기존 보안 공백**이다
  — 이 문서 이전에는 ADMIN 역할을 가진 계정이 있어도 그 역할이 실제로 어떤 특별한 접근을
  부여하는지 코드 어디에도 없었다(일반 인증 사용자와 동일). 각 후속 이슈가 실제로
  `@PreAuthorize`에 `ADMIN`을 넣기 전까지 이 공백은 유지된다.
- **Conduct/SchoolCamp는 도메인 자체가 아직 없다**: 이 문서가 정의한 그 두 도메인의 어드민
  기능은 코드가 하나도 없는 상태에서의 설계이므로, 실제 도메인 구현(`#58`/`#38`)이 먼저
  끝나야 착수할 수 있다 — 순서를 반드시 지킨다.
- **감사 로그 `detail` 컬럼(TEXT/JSON 문자열)**: 스키마가 없는 자유 형식이라 검색/필터가
  제한적이다. 나중에 검색 요구가 커지면 주요 필드를 별도 컬럼으로 분리하는 마이그레이션이
  필요할 수 있다 — 지금은 "무엇이 바뀌었는지 기록"이 목적이라 충분하다고 판단.
