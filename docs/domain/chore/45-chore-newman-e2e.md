# #45 QA에 Newman 기반 자동 e2e 테스트 도입 — 기획서

관련 이슈: [#45 QA에 Newman 기반 자동 e2e 테스트 도입](https://github.com/GBSW-ReMake/GONE-server-V1/issues/45)

## 개요/목적
지금 branch-workflow.md 10단계(QA/QC)는 실서버를 띄우고 사람이 curl/Postman으로 매번
수동 검증한다. 이 저장소는 이미 도메인별 Postman 컬렉션(`postman/collections/`)에
`pm.test(...)` 스크립트가 붙어있으므로, Newman(Postman 공식 CLI 러너)으로 그 자산을
그대로 재사용해 자동 e2e를 돌린다. 새 테스트 스크립트를 새로 쓰는 게 아니라 **이미 있는
컬렉션을 자동 실행**하는 것이 핵심이다.

이슈 본문이 "needs-discussion"이라 아래 결정 사항들은 승인 전 확정이 필요하다.

## 결정이 필요한 항목 (검토 요청)

### 1. Newman 실행 방식 — `npx newman`(권장) vs `package.json` 도입
이 저장소는 지금 순수 Gradle/Java 프로젝트로, Node/npm 관련 파일이 전혀 없다(`package.json`
없음, `.nvmrc` 없음). Newman을 쓰려면 Node 툴체인이 필요한데, 두 방식을 검토했다.

- **`npx newman`(권장)**: `package.json` 없이 실행 시점에 필요한 패키지를 받아온다.
  로컬에서 `npx --yes newman --version` → `6.2.2` 확인 완료(Node는 이미 개발 환경에
  설치돼 있다는 전제). 장점: 저장소에 Node 종속 파일을 아예 추가하지 않아 "순수 Java
  프로젝트"라는 현재 성격을 그대로 유지한다(YAGNI). 단점: 매 실행(특히 CI, 캐시 없는
  환경)마다 패키지를 새로 받아 몇 초~몇십 초 느리다.
- **`package.json` + `devDependencies`로 고정 버전 설치**: 실행이 빠르고 버전이 고정되지만,
  이 프로젝트에 Node 툴체인 자체를 공식으로 들이는 결정이라 `README.md`(현재 사실상
  비어있음)에 "Node.js 설치 필요"를 명시해야 하는 등 온보딩 비용이 늘어난다.

**권장**: 처음 도입이니 `npx newman`으로 가볍게 시작하고, 실행 속도가 실제로 문제가 되면
그때 `package.json` 고정으로 전환한다(이 프로젝트의 다른 곳에서도 반복해서 쓰는 YAGNI
판단과 동일한 결).

### 2. 실행 범위 — 이슈별 검증 폴더만 vs 컬렉션 전체
이슈 원문은 "이슈별 검증 폴더" 재사용을 언급하지만, 각 컬렉션에는 그 폴더 말고도
최상위 엔드포인트 항목 + "사전 준비" + "에러 케이스" 폴더가 있고 실제 `pm.test` 검증
로직 상당수가 "에러 케이스" 폴더에 있다(예: 403/404/409/400 조합). 이슈별 폴더만 도는
자동 실행은 회귀 방지 목적에 비해 커버리지가 좁다.

**권장**: **컬렉션 파일 전체**를 Newman으로 실행한다(`newman run gone-outing.postman_collection.json
-e gone-local-dev.postman_environment.json`). 각 컬렉션은 이미 "사전 준비 → 최상위
엔드포인트 → 이슈별 검증 폴더 → 에러 케이스" 순서(파일 안 배치 순서)로 사람이 위에서
아래로 실행하도록 설계돼 있고, Newman도 기본적으로 컬렉션에 나열된 순서 그대로 실행하므로
그 전제를 그대로 재사용할 수 있다. 다만 이는 **각 요청이 이전 요청이 설정한 환경 변수
(`outingCode` 등)에 의존하는 순서 결합을 그대로 물려받는다는 뜻**이라, 컬렉션 내부에서
항목 순서를 바꾸면 Newman 실행도 같이 깨질 수 있다는 제약을 그대로 안고 간다(기존
컬렉션 설계의 특성이지, 이 이슈에서 새로 만드는 문제는 아니다).

### 3. 서버 기동/대기/종료 — 신규 스크립트 위치와 "준비 완료" 판정 방법
이 저장소에 `scripts/` 같은 셸 스크립트 디렉토리가 아직 없다(code-style.md 컨벤션에도
없는 폴더). 새로 만들어야 한다.

- **위치**: `scripts/run-e2e.sh`(신규 폴더). 로컬(Windows Git Bash)과 CI(Ubuntu) 양쪽에서
  bash가 있어 그대로 재사용 가능.
- **"서버 준비 완료" 판정**: 이 프로젝트에 `spring-boot-starter-actuator`가 없어 표준
  `/actuator/health`가 없다. 특정 API 경로에 의존하면 그 경로가 바뀔 때 스크립트도 같이
  깨지므로, **TCP 포트 연결 여부**(`curl -s -o /dev/null http://localhost:9091` 반복 재시도,
  최대 60초 — #42 QA 때 실측한 기동 시간 약 25초에 여유를 둠)로 판정할 것을 제안한다.
  특정 엔드포인트의 존재/부재에 의존하지 않는 가장 느슨한 방법이다.
- **종료 처리**: `newman` 종료 코드(성공/실패)와 무관하게 항상 서버 프로세스를 정리해야
  한다(`trap ... EXIT`로 백그라운드 PID kill). Newman이 실패해도 서버가 좀비로 남으면
  다음 실행이 포트 충돌로 깨진다.

### 4. CI 통합 범위 — 어디까지 자동화할지 (가장 중요한 미결 사항)
`build-and-test` 잡은 이미 `mysql`/`redis` 서비스 컨테이너를 갖고 있어 Newman 실행에
필요한 인프라 자체는 재사용 가능하다. 하지만 **실제 살아있는 서버를 띄워 진짜 HTTP
요청을 보내는 e2e는, `contextLoads()`용 더미 자격증명(R2/NEIS)으로는 응답 내용까지
정확히 검증되지 않는 컬렉션이 있다**:
- `gone-meal`/`gone-timetable` 컬렉션의 `GET /meals`, `GET /timetables`는 서버가 NEIS
  오픈 API를 실제로 호출한다 — 더미 `NEIS_API_KEY`로는 그 응답 자체가 실패(또는 빈 값)할
  가능성이 높다.
- `gone-file` 컬렉션의 `upload-url`/`confirm`은 R2 프리사인드 URL 발급/확인을 탄다 —
  URL 서명 자체는 로컬 연산이라 더미 키로도 형식은 만들어지지만, `confirm`이 실제로 R2에
  파일이 존재하는지까지 검증하는지는 코드 재확인이 필요하다(이번 기획서 조사 범위 밖).

**두 가지 선택지 중 하나를 확정해야 한다**:
1. **CI에는 우선 `gone-auth`/`gone-user`/`gone-outing`처럼 외부 연동이 없는 컬렉션만
   Newman으로 돌린다.** NEIS/R2가 걸린 컬렉션은 이번 범위에서 제외하고 로컬 수동 QA로
   남긴다. 도입 비용이 가장 낮다.
2. **GitHub Secrets에 테스트용 실제 NEIS API 키/R2 자격증명을 추가로 등록해 전체
   컬렉션을 CI에서 돌린다.** 커버리지는 완전해지지만 실제 외부 서비스 키를 CI에 심는
   비용/리스크가 생기고(NEIS API 호출 한도, R2 테스트 버킷 오염 가능성), 그 키를 발급/
   관리하는 별도 작업이 필요하다.

**권장**: 1번(외부 연동 없는 컬렉션만 우선)으로 좁게 시작한다 — 이슈 본문의 "DB 등 연결
실패로 막히면 임의로 건너뛰지 않고 물어본다" 원칙과 같은 결로, 여기서도 임의로 전체
자동화를 확대하지 않고 범위를 좁혀 승인받는다.

### 5. branch-workflow.md 10단계 통합 방식
QA를 전부 대체하는 게 아니라 **회귀 확인을 자동화해 사람이 볼 부분을 줄이는 보조 수단**으로
건다. 제안 문구: "가능하면 `scripts/run-e2e.sh {도메인}`으로 관련 컬렉션을 먼저 자동
실행해 기존 회귀가 없는지 확인하고, 이번 이슈에서 새로 추가/변경된 케이스(신규 컬렉션
항목 포함)는 여전히 사람이 직접 확인한다." — 이번 `#42` QA처럼 "실제 시간이 지나야 하는"
시나리오(스케줄러 등)는 Newman 자동 실행만으로 커버되지 않으므로, 자동 e2e가 전부를
대체한다고 기획서에 쓰지 않는다.

## 작업 범위 (위 결정 반영 후 확정)
- [ ] `scripts/run-e2e.sh {domain}` 신규 — 서버 기동(dev 프로필) → 포트 준비 대기 →
      `npx newman run postman/collections/gone-{domain}.postman_collection.json -e
      postman/environments/gone-local-dev.postman_environment.json` → 종료 코드로 성공/실패
      판정 → 항상 서버 프로세스 종료
- [ ] CI(`ci.yml`)의 `build-and-test` 잡에 Newman 스텝 추가 — 위 "4. CI 통합 범위"에서
      승인된 컬렉션 목록만 대상
- [ ] `branch-workflow.md` 10단계에 위 "5." 문구 반영
- [ ] `docs/rules/`에 Newman 실행 규칙 문서 추가 여부 검토(다른 `*.md` 규칙 파일과 같은
      위치에 둘지, 이 기획서로 충분한지는 리뷰 시 확인)

## 데이터 모델 변경

## 영향 받는 기존 코드
- 신규 `scripts/` 디렉토리(이 프로젝트에 처음 도입되는 폴더 — code-style.md의 "새 폴더가
  필요하면 기획서에서 검토받는다" 원칙에 따라 이 절에 명시)
- `.github/workflows/ci.yml`: `build-and-test` 잡에 스텝 추가(신규 잡 분리는 하지 않음 —
  이미 있는 mysql/redis 서비스 재사용이 목적이라 같은 잡 안에 두는 게 자연스럽다)
- 기존 Postman 컬렉션/환경 파일 자체는 변경하지 않는다(이미 있는 자산 재사용이 이 이슈의
  전제).

## 리스크 및 고려사항
- **Node 툴체인 도입 자체가 이 저장소 최초 사례**다 — 위 "1." 항목 결정에 따라
  `README.md`(현재 사실상 비어있음)에 로컬 실행 전제 조건(Node 설치 여부)을 남길지도
  같이 검토한다.
- **컬렉션 요청 간 순서 결합(위 "2." 참고)**: 다른 이슈에서 그 컬렉션의 항목 순서를 바꾸면
  Newman 자동 실행이 이유 없이 깨질 수 있다 — 컬렉션 수정 시 순서 의존성을 인지하고
  바꾸도록 별도 규칙 문서에 남길지도 검토 대상.
- **CI에서 NEIS/R2 실 연동 컬렉션 제외(위 "4." 권장안 채택 시)**: `gone-meal`/
  `gone-timetable`/`gone-file`은 당분간 로컬 수동 QA로만 커버된다는 걸 명시적으로
  남겨야, 나중에 "왜 얘네는 자동화 안 됐지"라는 혼란이 없다.
