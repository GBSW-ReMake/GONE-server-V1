# 탈퇴 사용자 필터링 — 기능 기획서

> 관련 이슈: [#35 탈퇴/소프트 삭제 사용자가 조회·검색 결과에서 필터링되지 않음](https://github.com/GBSW-ReMake/GONE-server-V1/issues/35)
>
> 신규 엔드포인트가 없는 이슈다 — 기존 `User` 조회 경로 전체에 이미 있는 `deleted_at` 컬럼
> 필터를 일관되게 적용하는 것이 전부라, 아래 "설계 결정" 절이 이 기획서의 핵심이다.

## 개요/목적
`User` 엔티티에는 소프트 삭제용 `deleted_at` 컬럼이 이미 있지만(`V2__init_user_and_gbsw.sql`),
이 컬럼을 실제로 걸러 읽는 쿼리가 프로젝트 어디에도 없다. 탈퇴 처리(`deleted_at` 채우기)
기능 자체도 아직 없어 당장 실사용 영향은 없지만, 나중에 관리자 탈퇴 처리 화면이 생기는 순간
탈퇴한 학생/선생님이 로그인·검색·다른 도메인 조회에 그대로 노출되는 문제로 바로 이어진다.
스쿨캠핑(`#38`)의 팀원/선생님 검색·존재 확인이 이 리포지토리를 그대로 재사용하므로, 그
착수 전에 먼저 막아둔다.

## 정책 (스쿨캠핑 마스터 기획서 검토 중 확정, 2026-08-18)
- 졸업/자퇴/퇴학을 구분하지 않고 전부 "탈퇴" 하나로 묶는다 — 사유 구분 컬럼을 새로 두지
  않는다(왜 탈퇴했는지는 이 앱이 신경 쓸 정보가 아니라고 판단).
- 이미 있는 `User.deletedAt`을 탈퇴 여부의 단일 소스로 그대로 쓴다 — 신규 컬럼/enum 불필요.
- `deletedAt`을 채우는 시점: 학교 명단 엑셀 재업로드로 자동 추론하지 않는다
  (`GbswExcelImportService`가 아직 스텁이고, 있어도 "새 명단에 없어짐 = 탈퇴"는 엑셀 누락 등
  오탐 위험이 있어 자동화하기엔 이르다). **관리자가 수동으로 탈퇴 처리하면 그때 채운다** —
  그 수동 처리 화면/엔드포인트는 이번 범위가 아니라 별도 ADMIN 관리 페이지 몫이다.

## 설계 결정 — 엔티티 레벨 전역 필터(`@SQLRestriction`)
이슈 원문은 "`UserRepository`의 조회 계열 메서드(`findById`, `findByLoginId`,
`searchByRealNameContaining` 등)에 `deleted_at IS NULL` 조건을 일관되게 적용"이라고
제안했지만, 실제 코드를 보면 이 방식으로는 커버할 수 없는 구멍이 있다.

- `findById(Long)`은 `UserRepository`가 직접 선언한 메서드가 아니라 `JpaRepository`가
  제공하는 **상속 메서드**다. `outing`(`OutingService`, 담당 선생님 단건 조회),
  `timetable`(`TimetableService`), `user`(`UserService`, 내 프로필 조회)에서 이미 이
  메서드를 직접 호출하고 있는데, `UserRepository`에 커스텀 `@Query`를 새로 추가하는 방식으로는
  이 상속 메서드 자체를 오버라이드할 수 없다(시그니처가 같은 메서드를 새로 선언해도 Spring
  Data가 커스텀 구현으로 인식하게 하려면 별도 `QueryDslPredicateExecutor`류 인프라가
  필요한데, 이 프로젝트엔 그런 인프라가 없다 — 과한 도입이라 판단).
- `existsByGbsw`/`existsByLoginId`/`existsByName`도 마찬가지로 파생 쿼리라 메서드 시그니처
  자체를 바꾸지 않고는 조건을 끼워 넣을 수 없다.

그래서 리포지토리 메서드를 하나씩 고치는 대신, **`User` 엔티티에 Hibernate
`@SQLRestriction("deleted_at is null")`을 붙여 이 엔티티를 조회하는 모든 경로(파생 쿼리,
커스텀 `@Query`, `findById` 등 상속 메서드 포함)에 자동으로 `WHERE deleted_at IS NULL`이
붙게 한다.** Hibernate가 SQL을 생성하는 시점에 조건을 주입하는 방식이라 리포지토리 코드를
건드릴 필요가 없고, 나중에 `User`를 조회하는 새 메서드가 추가돼도(리뷰에서 놓치더라도)
자동으로 안전하다 — "탈퇴 필터를 빠뜨리는 실수 자체를 구조적으로 막는다"는 게 개별 메서드
수정보다 나은 지점이다.

- 이 프로젝트에 소프트 삭제 전역 필터 패턴이 처음 도입되는 사례다(기존에 재사용할 선례가
  없다 — code-style.md의 "새 패턴을 임의로 만들지 않는다" 원칙에 따라 이 절에 근거를
  남긴다).
- `deprecated`된 `@Where` 대신 Hibernate 6.3+에서 그 대체로 도입된 `@SQLRestriction`을
  쓴다(이 프로젝트는 Spring Boot 4.1.0 → Hibernate 7.x라 `@Where`는 이미 제거된 API다).
- **트레이드오프**: 관리자가 나중에 "탈퇴 취소(복구)" 또는 "탈퇴한 사용자까지 포함해서
  조회"해야 하는 화면(예: 탈퇴 계정 관리 페이지)이 생기면, `@SQLRestriction`이 걸린
  `UserRepository`로는 그 조회 자체가 불가능하다. 이번 범위에는 그런 기능이 없어 문제가
  되지 않지만, 나중에 필요해지면 별도 네이티브 쿼리 또는 `Session#disableFilter`류 예외
  경로를 그때 새로 만들어야 한다(YAGNI — 지금 미리 만들지 않는다).

## 변경 전/후 동작 차이
| 대상 | 변경 전 | 변경 후 |
|---|---|---|
| `userRepository.findById(id)` (모든 호출부) | 탈퇴 계정도 그대로 조회됨 | 탈퇴 계정이면 `Optional.empty()` |
| `findByLoginId`/`findFirstByLoginIdOrPhoneNumber` | 탈퇴 계정으로도 로그인 시도 시 조회됨 | 탈퇴 계정이면 조회 안 됨 → 기존 "존재하지 않는 계정" 처리 경로 그대로 재사용 |
| `existsByLoginId`/`existsByName` | 탈퇴 계정의 로그인 ID/별명도 "사용 중"으로 집계 | 탈퇴 계정의 값은 "사용 가능"으로 집계(재사용 가능해짐) — 회원가입 시 중복 체크 정책과 맞물리는 부분이라 아래 "리스크" 참고 |
| `searchByRealNameContaining` (`#32`) | 탈퇴 학생/선생님도 검색 결과에 노출 | 탈퇴 계정 제외 |
| `findByIdForUpdate` | 탈퇴 계정도 락 걸고 조회됨 | `@SQLRestriction`은 `@Query`가 명시된 메서드에도 동일하게 적용되므로 탈퇴 계정이면 조회 안 됨 |

## 데이터 모델 변경
없음 — `deleted_at` 컬럼은 이미 존재한다(`V2__init_user_and_gbsw.sql`). 신규 마이그레이션
불필요.

## 영향 받는 기존 코드
- `User` 엔티티(`@SQLRestriction` 어노테이션 추가)
- 간접 영향(코드 수정 없음, 동작만 바뀜): `UserService`, `OutingService`(담당 선생님 조회),
  `TimetableService` — 전부 `userRepository.findById`를 그대로 쓰고 있어 엔티티 레벨 필터만
  추가하면 별도 수정 없이 자동 적용됨
- 테스트: 탈퇴 계정을 만들어(`deletedAt` 채운 `User` 저장) 위 표의 각 메서드가 그 계정을
  더 이상 반환하지 않는지 검증하는 테스트 추가 필요(`UserRepositoryTest` 신규 또는 기존
  테스트 확장)

## 리스크 및 고려사항
- **회원가입 중복 체크 정책과의 상호작용**: `existsByLoginId`/`existsByName`이 탈퇴 계정의
  값을 "사용 가능"으로 취급하게 되는데, 이게 의도한 동작인지(탈퇴한 학생의 아이디/별명을
  다른 사람이 즉시 재사용 가능해도 되는지) 확답이 없다 — 탈퇴 기능 자체가 아직 없어 지금은
  실제로 발생하지 않는 시나리오지만, 나중에 탈퇴 처리 화면이 생기면 바로 마주치게 된다.
  이번 범위에서는 "일단 재사용 허용"으로 두고 별도 예외 처리를 추가하지 않는다 —
  문제라고 판단되면 그때 별도 이슈로 다룬다.
- **`@SQLRestriction`은 이 프로젝트 첫 도입 사례**라 팀원이 낯설 수 있다 — 나중에 `User`를
  조회했는데 결과가 예상과 다르면(예: 분명히 있는 계정인데 안 나옴) 이 어노테이션을 먼저
  의심하도록, 엔티티 필드 주석에도 짧게 남겨둔다.
- **하위 호환성**: 기존에 탈퇴 계정을 조회하던 코드가 없어(탈퇴 기능 자체가 없었으므로)
  이 변경으로 깨지는 기존 동작은 없다.
- **성능**: `deleted_at IS NULL` 조건은 단순 컬럼 비교라 기존 인덱스 활용에 지장이 없다.
  다만 이 조건에 의존하는 조회가 많아지면(예: 학생 전체 목록) 별도 인덱스가 필요할 수
  있다 — 이번 범위(단건/검색)에서는 불필요, 실제 데이터가 쌓인 뒤 재검토.
