# #17 로그인 ID/전화번호 겸용 입력 — QA/코드 리뷰 결과

관련 이슈: https://github.com/GBSW-ReMake/GONE-server-V1/issues/17
관련 기획서: [17.md](./17.md)

## 자동 테스트
- `./gradlew build`, `./gradlew test`, `./gradlew checkstyleMain checkstyleTest` 모두 로컬 통과.
- 신규/수정 테스트:
  - `UserDetailsServiceImplTest` — loginId로 로그인, 전화번호로 로그인, 둘 다 못 찾는 케이스 3종
    추가/수정. `findFirstByLoginIdOrPhoneNumber(identifier, identifier)` 호출 인자까지 검증.
  - `AuthControllerTest` — 로그인 요청 바디 JSON 키를 `loginId` → `identifier`로 갱신, 전화번호로
    로그인 요청을 보내는 케이스 추가.
  - `AuthServiceTest`는 `LoginRequest`를 위치 기반 생성자로만 사용해서(`new LoginRequest("id", "pw")`)
    필드명 변경의 영향을 받지 않아 수정 불필요.

## QA — 실제 환경 검증

### 검증한 것
- 로컬 MySQL(`gone` 스키마, Flyway V6까지 적용된 실제 dev DB)에 실제 서버(`./gradlew bootRun`,
  `dev` 프로필)를 띄운 뒤 `POST /api/v1/auth/login`에 직접 요청을 보내 확인:
  1. **기존 전화번호(`01050682869`, DB에 실존하는 `testuser01`의 번호) + 틀린 비밀번호** →
     `401 AUTH_007` (SQL 에러/500 없이 phone_number 분기가 정상적으로 조회까지 도달함을 확인)
  2. **기존 loginId(`testuser01`) + 틀린 비밀번호** → 동일하게 `401 AUTH_007` (기존 loginId
     분기 회귀 없음)
  3. **존재하지 않는 identifier** → 동일하게 `401 AUTH_007` (두 컬럼 모두 매칭 실패 시에도
     예외 없이 깨끗하게 처리됨)
  - 세 요청 모두 서버 로그에 예외 스택트레이스가 찍히지 않음을 확인 — `findFirstByLoginIdOrPhoneNumber`
    파생 쿼리가 실제 스키마(두 컬럼 모두 unique 인덱스)에 대해 SQL로 정상 번역되어 실행됨을
    간접 확인.
  - 사용한 계정은 #11 QA 때 만들어진 기존 테스트 데이터를 그대로 조회만 했고, 새로 데이터를
    쓰거나 지우지 않았다(읽기 전용 검증).

### 검증하지 못한 것 (환경 제약)
- **로그인 성공(200) 케이스를 실제 서버로 끝까지 검증하지 못함.** 이 환경에는 로컬 Redis가
  설치되어 있지 않고 Docker Desktop도 기동되어 있지 않아, `AuthService.issueTokens()`의
  Refresh Token 저장(`redisRepository.save`) 단계를 실행할 수 없었다. 비밀번호가 맞는 계정으로
  로그인을 시도하면 인증 자체(`AuthenticationManager.authenticate`)는 통과하지만 이후 Redis
  저장 단계에서 별도 인프라 오류가 났을 것으로 예상되며, 이는 이번 변경(식별자 조회 로직)과
  무관한 기존 환경 제약이다. `UserDetailsServiceImplTest`에서 Mockito로 성공 케이스(로그인
  ID/전화번호 각각)를 이미 커버하고 있어, 조회 로직 자체의 정확성은 단위 테스트로 보완됨.
- 실제 비밀번호를 아는 계정이 없어 "전화번호 + 올바른 비밀번호"로 인증까지 성공하는 케이스는
  기존 테스트 데이터로 실행하지 못했다(비밀번호는 해시로만 저장되어 있어 알 수 없음). 새 계정을
  만들어 검증하는 방법도 있었으나, Gbsw fixture까지 함께 만들어야 해서 이번 QA 범위에서는
  생략하고 위 3케이스(비밀번호 불일치/미존재)로 SQL 실행 정상 여부만 확인했다.

## 코드 리뷰 (자체 점검)

### 확인한 항목 (문제 없음)
- `docs/17.md`에 명시된 대로 `findFirstBy...`를 사용해 loginId/phoneNumber 우연 충돌 시에도
  `IncorrectResultSizeDataAccessException` 없이 1건만 반환하도록 되어 있음 — 코드 확인 완료.
- `LoginRequest` 필드명 변경(`loginId` → `identifier`)이 `AuthService.login()`, `AuthController`,
  테스트 전반에 일관되게 반영됨. `SignUpRequest.loginId`, `/login-id/check` 엔드포인트는 이번
  변경과 무관한 별개 필드/엔드포인트라 손대지 않음(기획서 범위와 일치).
- 기획서의 "영향 받는 기존 코드/테스트" 목록에는 없었지만 실제로는 `AuthControllerTest`의 로그인
  요청 바디 JSON 키도 함께 바꿔야 했다 — 발견 즉시 `docs/17.md`에 반영해 최신 상태로 유지함
  (branch-workflow 8단계 규칙).
- 성능/쿼리 횟수는 기존과 동일(단일 조회 1회) — 기획서의 리스크 분석과 일치, 추가 조치 불필요.

### 이슈 없음
이번 조사에서는 심각도가 있는 새 버그를 찾지 못했다.
