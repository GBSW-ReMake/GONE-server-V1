# #11 역할(Role) 기반 권한 시스템 + AuthenticationManager 도입

관련 이슈: https://github.com/GBSW-ReMake/GONE-server-V1/issues/11

## 개요/목적
현재 인증(JWT)만 있고 권한(Role) 구분이 전혀 없다. 학생/선생님/관리자 구분과, 학생회·선도부·
총무부 등 부서 기반 권한이 필요해질 예정이라, 한 사용자가 여러 역할을 동시에 가질 수 있는
다대다(User↔Role) 구조로 미리 도입한다.

겸사겸사 로그인 시점 자격증명 검증도 지금의 수동 검증(`passwordEncoder.matches()` 직접 호출)에서
Spring Security 표준 `AuthenticationManager`/`UserDetailsService` 기반으로 전환한다. **이 전환은
로그인(자격증명 검증) 시점에만 적용되고, 로그인 이후 매 요청의 JWT 인증(`JwtAuthenticationFilter`,
`UserPrincipal`)은 지금처럼 완전히 별개의 stateless 구조로 유지한다** — 이 둘은 서로 다른 관심사이며,
이번 도입으로 하나가 다른 하나를 대체하지 않는다.

**이번 이슈는 새 엔드포인트를 추가하지 않고, 기존 서비스 로직(회원가입, 로그인 검증, JWT 발급,
인증 필터)을 수정하는 유형이다.**

## 데이터 모델

### `role` 테이블 (신규)
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | BIGINT PK | |
| code | VARCHAR(30) UNIQUE | 역할 코드 (예: `STUDENT`, `DISCIPLINE`) |
| name | VARCHAR(30) | 화면 표시용 한글명 (예: "선도부") |

시드 데이터 (9개, 마이그레이션에 INSERT로 포함):
| code | name |
|---|---|
| STUDENT | 학생 |
| TEACHER | 선생님 |
| ADMIN | 관리자 |
| STUDENT_COUNCIL | 학생회 |
| DISCIPLINE | 선도부 |
| GENERAL_AFFAIRS | 총무부 |
| ENVIRONMENT | 환경부 |
| BROADCASTING | 방송부 |
| ATHLETICS | 체육부 |

### `user_role` 테이블 (신규, N:M 조인)
| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | BIGINT PK | |
| user_id | BIGINT FK → user.id | |
| role_id | BIGINT FK → role.id | |
| created_at | DATETIME | 역할 부여 시각 |

`UNIQUE(user_id, role_id)`로 같은 역할 중복 부여 방지.

### 마이그레이션
`V6__add_role_and_user_role.sql` — `role` 테이블 생성 + 9개 시드 INSERT, `user_role` 테이블 생성.

## 변경되는 기존 로직

### 1. 회원가입 시 기본 역할 자동 부여 (`AuthService.signUp`)
`Gbsw.type`(`STUDENT`/`TEACHER`)에 대응하는 기본 역할(`STUDENT`/`TEACHER`)만 가입 완료 시점에
`UserRole`로 자동 부여한다.

**⚠️ 회원가입 로직이 부여할 수 있는 role은 `STUDENT`/`TEACHER` 단 둘뿐이다.** 학생회/선도부/
총무부/환경부/방송부/체육부/관리자 등 그 외 모든 role은 `Gbsw`에 어떤 정보가 있든 회원가입
시점에 **절대 자동 부여하지 않는다** — 오직 관리자가 role 부여 API(#15, 범위 밖 참고)로만
사후에 부여할 수 있다. `AuthService.signUp()`이 `Gbsw.type` 외의 값을 근거로 다른 role을
추론/부여하지 않는지 코드 리뷰 시 반드시 확인한다.

### 2. JWT에 역할 정보 포함 (`JwtProvider`)
- `createAccessToken(Long userId, Set<String> roleCodes)`로 시그니처 변경, `roles` 클레임(문자열
  배열)을 추가한다. Refresh Token에는 역할을 담지 않는다(재발급 시 최신 역할을 다시 조회해서
  발급 — 역할이 바뀐 뒤에도 예전 Refresh Token으로 옛 역할이 담긴 Access Token이 재발급되는
  것을 방지).
- `getUserIdFromAccessToken`와 별개로, 클레임에서 역할 목록을 꺼내는 메서드를 추가한다.

### 3. 인증 필터가 역할을 권한으로 매핑 (`JwtAuthenticationFilter`)
현재 `new UsernamePasswordAuthenticationToken(principal, null, List.of())`로 권한이 항상
빈 리스트인데, 토큰의 `roles` 클레임을 `SimpleGrantedAuthority("ROLE_" + code)` 목록으로
변환해 담는다. 이렇게 해야 `SecurityConfig`에서 `hasRole("ADMIN")` 같은 인가 규칙을 쓸 수 있다.
**`UserPrincipal`은 그대로 `record UserPrincipal(Long userId)` 유지** — role은 principal이 아니라
`Authentication`의 `authorities` 자리에만 싣는다 (Spring Security가 이미 인가 판단에 쓰는 표준 자리).

### 4. 로그인 검증을 `AuthenticationManager` 기반으로 전환 (신규)
- **`common/security/AuthUserDetails`** (신규): `UserDetails` 구현체. `User` 엔티티 자체가 아니라
  이를 감싸는 별도 클래스로 만든다 (JPA 엔티티를 Spring Security 인터페이스와 결합시키지 않기
  위함). `getUsername()` → `loginId`, `getPassword()` → `passwordHash`, `getAuthorities()` →
  role code들을 `ROLE_*` 권한으로. `isEnabled()`/`isAccountNonLocked()`/`isAccountNonExpired()`/
  `isCredentialsNonExpired()`는 전부 `true` 고정 (계정 잠김/정지 개념 자체가 아직 없음 — 생기면
  그때 이 필드들을 실제 컬럼과 연결).
- **`common/security/UserDetailsServiceImpl`** (신규) `implements UserDetailsService`:
  `loadUserByUsername(loginId)` → `userRepository.findByLoginId` + role 목록 조회 →
  `AuthUserDetails`로 래핑. 없으면 `UsernameNotFoundException` (Spring이 기본으로
  `BadCredentialsException`으로 감춰줘서, 지금처럼 "아이디 없음"과 "비번 틀림"을 구분 안 하는
  정책이 자동으로 유지됨).
- **`SecurityConfig`**: `AuthenticationManager` 빈 노출 (`DaoAuthenticationProvider`에
  `UserDetailsServiceImpl` + 기존 `PasswordEncoder` 연결).
- **`AuthService.login()`**: `userRepository.findByLoginId` + `passwordEncoder.matches()` 수동
  검증 코드를 제거하고, `authenticationManager.authenticate(new
  UsernamePasswordAuthenticationToken(loginId, password))` 호출로 대체. 실패 시
  `AuthenticationException`을 잡아서 지금과 동일하게 `CustomException(INVALID_CREDENTIALS)`로
  변환 (에러 응답 포맷/계정 열거 방지 정책 그대로 유지).
- **`reissue()`는 대상 아님**: 재발급 시점엔 원본 비밀번호가 없어(Refresh Token만 있음)
  `AuthenticationManager`를 쓸 수 없다. 지금처럼 `userRepository`/역할 조회로 직접 최신 role을
  가져와 토큰을 재발급한다.

### 5. `AuthService.login`/`reissue`도 역할을 함께 조회해서 토큰 발급
`login()`은 `AuthUserDetails`에 이미 담겨온 role 목록을 그대로 쓰고, `reissue()`는 `UserRole`을
직접 조회해 role code 목록을 만들어 `JwtProvider.createAccessToken`에 전달한다.

## 영향 받는 기존 코드/테스트
- `AuthService`, `AuthServiceTest`: `login()` 테스트를 `AuthenticationManager` 목킹 방식으로 전면
  수정. signUp/reissue 관련 테스트에 role 부여/조회 검증 추가.
- `JwtProvider`, `JwtProviderTest`: 토큰 생성 시그니처 변경에 따른 테스트 수정.
- `JwtAuthenticationFilter`, `JwtAuthenticationFilterTest`: 권한 매핑 로직 추가 및 테스트.
- `SecurityConfig`: `AuthenticationManager` 빈 추가. 당장 role 기반으로 막는 엔드포인트는 없음
  (기존 permitAll/logout만 유지) — 이번 이슈는 "역할을 매길 수 있고 토큰에 실어 나를 수 있는"
  기반만 만든다.
- 신규 `AuthUserDetails`, `UserDetailsServiceImpl`에 대한 단위 테스트 추가.

## 리스크 및 고려사항
- **Refresh Token에 role을 안 담는 이유**: role은 시간에 따라 바뀔 수 있는 정보라, Access
  Token에만 실어서 만료(30분)마다 최신 상태로 갱신되게 한다.
- **`AuthenticationManager` 도입이 실제로 풀어주는 문제 / 안 풀어주는 문제**: 이건 로그인
  "시도"를 검증하는 방식을 표준화하는 것이지, 로그인 이후 세션 중간에 계정을 정지시키는 문제는
  풀어주지 않는다 (JWT는 한 번 발급되면 만료 전까지 유효하므로, 정지는 재발급 시점에 role/상태를
  다시 확인하는 별도 로직이 필요 — 이번 이슈 범위 밖).
- **⚠️ 확정된 미래 요구사항: 관리자가 role을 바꾸면 즉시 로그아웃(강제 재로그인)되어야 함.**
  부서별로 보여줄 페이지가 달라서, role이 바뀐 사용자가 예전 role의 화면을 계속 보면 안 된다.
  이건 #15("role 부여/변경 API")에서 구현할 대상이지만, **지금 이 이슈의 설계가 그걸
  가능하게 해두는지**를 미리 점검해야 한다:
  - Refresh Token은 이미 로그아웃과 같은 방식(Redis에서 삭제)으로 즉시 무효화할 수 있다 —
    role 변경 시 해당 유저의 `RedisKeyType.REFRESH_TOKEN`을 지우면, 다음 `/reissue` 요청부터는
    막힌다(재로그인 필요).
  - **하지만 이미 발급된 Access Token은 이 방식으로 막을 수 없다** — stateless라 만료
    시간(현재 30분) 전까지는 옛 role이 담긴 채로 계속 유효하다. 즉 "즉시"를 문자 그대로
    보장하려면 Access Token TTL을 지금(30분)보다 훨씬 짧게(예: 1~5분) 줄이고 Refresh Token
    rotation에 의존하는 쪽으로 가거나, 별도의 Access Token 무효화 검사(매 요청마다 Redis
    조회 — stateless의 이점을 일부 포기)를 추가해야 한다.
  - **이번 이슈(#11)에서 결정할 것**: Access Token TTL을 지금 유지(30분)할지, 미리 줄여둘지는
    다음 이슈(#15, role 변경 API) 설계 시점에 함께 정하는 걸 제안한다. 다만 role 클레임을 Access
    Token에 넣기로 한 지금 설계 자체는 두 방향(TTL을 줄이는 방향이든, 무효화 검사를 추가하는
    방향이든) 모두와 호환되므로, 이번 이슈를 이 이유로 다시 설계할 필요는 없다.
- **`UserDetails`의 잠김/만료 필드는 지금 전부 `true` 고정**: 실제 계정 상태 컬럼이 없어서다.
  나중에 계정 정지 기능이 생기면 그때 `User`(또는 별도 상태 테이블)에 컬럼을 추가하고
  `AuthUserDetails`가 이를 반영하도록 확장한다.
- **기존 유저(마이그레이션 시점에 이미 가입된 사용자)에게도 기본 역할을 부여해야 하는가**:
  이번 서비스는 아직 운영 전(가입자 없음)이라 별도 백필 스크립트는 불필요하다고 판단.

## ⚠️ 이번 이슈 범위 밖 (별도 이슈로 분리 제안)
- 관리자가 특정 유저에게 부서 역할(학생회/선도부 등)을 부여/회수하는 **API**는 포함하지 않는다.
  지금은 시드 데이터와 데이터 모델, JWT/필터 배관만 만들고, 실제 "누구에게 어떤 부서 역할을
  주는지"는 #15(관리자 역할 부여/변경 API)에서 엔드포인트 1~2개로 다룰 걸 제안.
  - **#15의 필수 요구사항(확정)**: role 변경 시 대상 유저를 **즉시 로그아웃 처리하고
    재로그인을 유도**해야 한다 (부서별로 보여줄 페이지가 달라서, 바뀌기 전 role로 화면에
    계속 접근하면 안 됨). 위 리스크 항목에 기술적 방법(Refresh Token 즉시 삭제로 재발급
    차단 + Access Token TTL 조정 또는 무효화 검사)을 적어뒀으니, 그 이슈의 기획서 작성 시
    이 항목부터 확정하고 시작할 것.
- `SecurityConfig`에 역할 기반으로 실제로 막는 엔드포인트도 아직 없음(막을 대상 API가 아직
  없어서). 특정 API를 역할로 제한하는 요구가 생기면 그때 추가.
- 계정 잠김/정지, 세션 중간 무효화 로직은 포함하지 않는다 (위 리스크 항목 참고).
- 관리자 웹 콘솔용 세션 기반 로그인(별도 `SecurityFilterChain`)은 포함하지 않는다 — 필요해지면
  별도 이슈.
