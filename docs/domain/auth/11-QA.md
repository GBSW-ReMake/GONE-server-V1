## QA — 실제 환경 검증

### 검증한 것
- 실제 로컬 MySQL에 Gbsw/User/UserRole row를 만들어 실제 `AuthenticationManager` 빈으로
  `authenticate()` 직접 호출 → 다음을 확인:
  - 올바른 비밀번호 → 인증 성공, `AuthUserDetails`에 담긴 role이 실제 DB의 `UserRole`과 일치
  - 틀린 비밀번호 → `BadCredentialsException`
  - 존재하지 않는 아이디 → 역시 `BadCredentialsException`으로 감춰짐 (계정 열거 방지 유지 확인)
  - `Hibernate ddl-auto: validate` 모드로 `contextLoads()`가 통과함 — `Role`/`UserRole` 엔티티
    매핑이 `V6` 마이그레이션 스키마와 정확히 일치함을 간접 확인
- 검증에 사용한 테스트 데이터는 확인 후 삭제 완료.

### 참고 — Spring Security가 자동으로 붙이는 추가 권한
실제 인증 결과의 `authorities`에 `ROLE_STUDENT` 외에 `FactorGrantedAuthority
[authority=FACTOR_PASSWORD, ...]`가 함께 붙는 것을 확인했다 (Spring Security가 어떤 인증
수단(factor)을 썼는지 자동으로 표시하는 최신 기능). JWT `roles` claim은 `authentication.getAuthorities()`가
아니라 `AuthUserDetails.roleCodes()`에서 직접 뽑으므로 이 값이 섞여 들어가지 않는다 — 영향 없음.

## 코드 리뷰 (자체 점검)

### 참고 — DB 조회 횟수 증가 (버그 아님, 의도된 트레이드오프)
- `login()`: 기존엔 `findByLoginId` 1회였는데, 이제 `UserDetailsServiceImpl`의 조회 1회 +
  role 조회 1회로 총 2회. role을 JWT에 실어야 하므로 필요한 조회.
- `reissue()`: 기존엔 role 조회가 없었는데, 최신 role을 반영하려고 매 재발급마다 1회 추가.
  `docs/11.md`에 이미 "role이 바뀐 뒤에도 옛 role이 계속 실려나가는 것을 방지"하려는 의도로
  문서화되어 있음.
- 로그인/재발급 빈도를 고려하면 이 정도 추가 조회는 무시할 수준으로 판단, 별도 조치 없음.

### 확인한 항목 (문제 없음)
- `UserRoleRepository.findRoleCodesByUserId`는 JPQL 프로젝션(`select ur.role.code from ...`)이라
  `UserRole`/`Role` 엔티티를 완전히 로드하지 않고 SQL JOIN으로 코드만 바로 가져온다 — N+1이나
  트랜잭션 밖 지연 로딩 문제 없음.
- `AuthService.signUp()`의 역할 부여가 `@Transactional` 안에서 `userRepository.save()`와 같은
  트랜잭션에 묶여 있어, 역할 부여가 실패하면 계정 생성도 함께 롤백된다 (역할 없는 계정이 남는
  것을 방지).
- `AuthUserDetails`의 잠김/만료 필드는 인터페이스 기본값(`true`) 그대로 사용 — 기획서에 명시한
  대로 계정 상태 컬럼이 없는 현재 상태와 일치.

### 이슈 없음
이번 조사에서는 심각도가 있는 새 버그를 찾지 못했다. #10에서 나온 미해결 항목(reissue rotation
race condition, Refresh Token TTL 이중 관리)은 이번 이슈 범위 밖이며 `docs/10-QA.md`에 이미
정리되어 있다.
