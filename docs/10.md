# #10 로그인 기능 구현 (JWT + Redis RT 저장)

관련 이슈: https://github.com/GBSW-ReMake/GONE-server-V1/issues/10

## 개요/목적
회원가입(#8/#9)까지 끝난 사용자가 서비스를 이용하려면 로그인이 필요하다.
JWT Access/Refresh 토큰 방식으로 인증하고, Refresh Token은 Redis에 저장/검증한다.

## 이슈 범위
`branch-workflow.md` 규칙상 이슈 1개당 엔드포인트 1~2개가 원칙이지만, 로그인/재발급/로그아웃
3개는 로그인 없이는 재발급도 로그아웃도 의미가 없어 하나로 묶기로 승인됨 (검토 완료).

## 엔드포인트 명세

### 1. `POST /api/v1/auth/login` — 로그인
- 인증: 불필요 (공개 API)
- Request (`LoginRequest`)
  | 필드 | 타입 | 비고 |
  |---|---|---|
  | loginId | String | |
  | password | String | |
- Response 성공 (`TokenResponse`, 200)
  | 필드 | 타입 | 비고 |
  |---|---|---|
  | accessToken | String | |
  | refreshToken | String | |
  | accessTokenExpiresIn | long | 초 단위 |
- 에러
  | 상황 | ErrorCode | 상태코드 |
  |---|---|---|
  | loginId 없음 / 비밀번호 불일치 | `AUTH_007 INVALID_CREDENTIALS` | 401 |

  → 어떤 쪽이 틀렸는지 구분하지 않고 동일 메시지("아이디 또는 비밀번호가 일치하지 않습니다") 사용 (계정 존재 여부 추측 방지).
- 처리
  1. `userRepository.findByLoginId` 조회, 없으면 `INVALID_CREDENTIALS`
  2. `passwordEncoder.matches`로 비밀번호 검증, 불일치 시 `INVALID_CREDENTIALS`
  3. `JwtProvider`로 Access/Refresh Token 발급
  4. Refresh Token을 Redis에 저장 (`RedisKeyType.REFRESH_TOKEN`, key: `userId`, value: refreshToken, TTL 14일)

### 2. `POST /api/v1/auth/reissue` — Access Token 재발급
- 인증: 불필요 (Refresh Token 자체가 인증 수단)
- Request (`ReissueRequest`)
  | 필드 | 타입 | 비고 |
  |---|---|---|
  | refreshToken | String | |
- Response 성공 (`TokenResponse`, 200 — 로그인 응답과 동일한 DTO 공유, 아래 참고)
  | 필드 | 타입 | 비고 |
  |---|---|---|
  | accessToken | String | 새로 발급 |
  | refreshToken | String | 회전(rotate)해서 새로 발급 |
  | accessTokenExpiresIn | long | 초 단위 |
- 에러
  | 상황 | ErrorCode | 상태코드 |
  |---|---|---|
  | 서명 무효/만료된 토큰 | `AUTH_008 INVALID_REFRESH_TOKEN` | 401 |
  | Redis에 저장된 값과 불일치(이미 재발급되어 폐기됨 등) | `AUTH_008 INVALID_REFRESH_TOKEN` | 401 |
- 처리
  1. JWT 서명/만료 검증
  2. Redis에 저장된 RT와 요청받은 RT가 일치하는지 확인 (재사용 탐지)
  3. 일치하면 AT/RT 모두 재발급, Redis 값 갱신 (Rotation)

### 3. `POST /api/v1/auth/logout` — 로그아웃
- 인증: **필요** (Access Token, `Authorization: Bearer {accessToken}`)
- Request: 없음 (본문 없음)
- Response 성공: 200, `ApiResponse<Void>`
- 에러
  | 상황 | ErrorCode | 상태코드 |
  |---|---|---|
  | Access Token 없음/무효/만료 | `COMMON_002 UNAUTHORIZED` | 401 |
- 처리: Access Token에서 userId 추출 → Redis에서 해당 유저의 Refresh Token 삭제

## 기존 로직/코드 변경
- `common/config/SecurityConfig.java`: 현재 `anyRequest().permitAll()` → `/api/v1/auth/logout`만 인증 필요하도록 수정, JWT 인증 필터 추가.
  (다른 기존 API는 그대로 permitAll 유지 — 이번 이슈 범위 밖)
- `build.gradle`: JWT 라이브러리 의존성 추가 (`io.jsonwebtoken:jjwt-api/impl/jackson` 0.12.x)
- `common/redis/RedisKeyType.java`: `REFRESH_TOKEN` 항목 추가 (prefix `auth:refresh:`, TTL 14일)
- `auth/exception/AuthErrorCode.java`: `INVALID_CREDENTIALS`(AUTH_007), `INVALID_REFRESH_TOKEN`(AUTH_008) 추가
- 신규 패키지 `common/security`: `JwtProvider`, `JwtProperties`, `JwtAuthenticationFilter`, `UserPrincipal`
  - `UserPrincipal`은 `record UserPrincipal(Long userId)` 형태의 경량 커스텀 principal.
    풀 `UserDetails`(username/password/authorities 로딩용)는 폼 로그인을 쓰지 않는 이 프로젝트엔 불필요하다고 판단.
  - `JwtAuthenticationFilter`가 Access Token의 `userId` claim을 추출해
    `new UsernamePasswordAuthenticationToken(new UserPrincipal(userId), null, authorities)`를 `SecurityContextHolder`에 세팅.
  - `logout` 컨트롤러는 `@AuthenticationPrincipal UserPrincipal principal`로 `userId`를 받아 Redis에서 RT 삭제.
- `application.yml` / `application-dev.yml`: `jwt.secret`, `jwt.access-token-expiration`, `jwt.refresh-token-expiration` 추가

## 데이터 모델 변경
- 없음 (Flyway 마이그레이션 불필요). Refresh Token은 DB가 아닌 Redis에만 저장.

## 영향 받는 기존 코드/테스트
- `SecurityConfig` 수정에 따라 기존 컨트롤러 테스트(`@WebMvcTest` 사용 시)에 시큐리티 컨텍스트 영향 있는지 확인 필요.
- 기존 `AuthControllerTest`, `PhoneAuthControllerTest`는 영향 없을 것으로 예상 (permitAll 경로 유지).

## 리스크 및 고려사항
- **토큰 만료 시간**: Access 30분 / Refresh 14일로 확정.
- **RT 회전(Rotation) 정책**: 재발급 시마다 RT를 새로 발급 (탈취 시 재사용 탐지 가능). 재사용
  탐지 시 추가 조치(전체 세션 무효화 등)는 이번 범위에서 제외하고 단순 거부만 처리.
- **JWT 시크릿 관리**: `application-dev.yml`(gitignored)에 평문으로 저장, CI는 더미 값 사용.
- **로그인 실패 메시지**: 아이디/비밀번호 중 무엇이 틀렸는지 노출하지 않음 (보안).
- **로그인/재발급 응답 DTO 통합**: 초안에서는 `LoginResponse`/`ReissueResponse`로 분리 계획했으나,
  필드가 완전히 동일해 구현 시 `TokenResponse` 하나로 통합함 (불필요한 중복 DTO 방지).
- **멀티 디바이스 로그인 시 이전 세션 무효화 (단일 세션 정책)**: Refresh Token이 `userId`로만
  키잉되어, 같은 계정으로 다른 기기에서 로그인하면 이전 기기의 Refresh Token이 Redis에서
  덮어써진다. 검토 결과 **현재는 멀티 디바이스 지원이 불필요하다고 판단해 의도된 동작으로
  확정**함. 필요해지면 별도 이슈로 분리해 `userId:deviceId` 키 구조 등으로 확장.
