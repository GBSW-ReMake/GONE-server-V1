# #20 회원가입 시 학적 기반 기본 닉네임 자동 생성 + 자유 편집 API

관련 이슈: https://github.com/GBSW-ReMake/GONE-server-V1/issues/20
(대체된 이전 이슈: #19 "회원가입 시점에 프로필 사진 업로드 지원" — 설계 방향이 바뀌어 폐기)

## 개요/목적
회원가입 시 닉네임(`User.name`)을 사용자가 직접 입력하지 않고, 서버가 학적 정보(`Gbsw`)를
이용해 자동으로 채워준다. 프로필 사진과 마찬가지로 "가입은 최소 정보로 빠르게 끝내고, 이름/사진은
가입 후 자유롭게 커스터마이징"하는 방향이다. 이번 이슈에서 이름 자동 생성 + 이름/프로필 사진을
각각 나중에 바꾸는 API까지 함께 정리한다.

**기본 닉네임 형식**
- 학생: `{학년 1자리}{반 1자리}{번호 2자리 0채움}{학적 실명}` — 학번은 항상 정확히 **4자리
  고정**이다. 이 학교는 한 학년에 반이 4개뿐이라 `classNo`는 항상 1자리(1~4)이고, `number`는
  2자리로 0채움한다. 예: 3학년 2반 5번 정문경 → `3205정문경`, 3학년 1반 11번 정문경 →
  `3111정문경`.
  - `Gbsw` 테이블에 이미 `(grade, class_no, number)` 유니크 제약(`uq_class_slot`)이 있고,
    학번 문자열이 항상 고정 4자리이므로 서로 다른 (학년,반,번호) 조합이 같은 4자리 문자열을
    만들 수 없다. 즉 **학생 쪽은 중복 처리(재시도/충돌 회피)가 전혀 필요 없다** (아래 "리스크"
    항목에 근거 정리).
- 교사: 학번이 없으므로 `T-{랜덤 3자리}-{학적 실명}` — 예: `T-a1b-김선생`. 동명이인 교사가
  있으면 문자열이 겹칠 수 있으므로, `existsByName`으로 확인 후 겹치면 랜덤 3자리를 다시 뽑아
  재시도(최대 5회)한다. 그마저도 우연히 다 겹치는 극희귀 상황은 기존과 동일하게 DB unique 제약
  위반 → `DataIntegrityViolationException` → `409`(기존 `AuthControllerTest`에 이미 있는
  경합 처리 패턴)로 안전하게 흡수된다.
- 프로필 사진은 계속 선택(optional)이며, 기본값 없음(`null`).

## 클라이언트 플로우
프론트는 한 화면에 한 항목씩 입력받는 단계형 UI를 쓴다: **아이디 → 비밀번호 → 전화번호 인증 →
이름 → 프로필 사진**. 화면 순서 자체는 보안과 무관하다(아래 "왜 화면 순서가 보안에 영향 없는가"
참고) — 이 순서는 순수 UX 판단이고, 다르게 바뀌어도 아래 API 계약은 그대로 유효하다.

실제 계정 생성은 **"전화번호 인증" 단계에서 `ticket`을 받는 순간**(=`loginId`/`password`/
`phoneNumber`/`ticket` 네 가지가 모두 모인 시점)에 일어난다. 그 앞 단계(아이디/비밀번호)는
값을 모으기만 할 뿐 계정을 만들지 않는다.

1. **아이디**: 입력할 때마다 `GET /auth/login-id/check`로 중복 확인. "다음"은 로컬 검증만.
2. **비밀번호**: 로컬 검증만(형식 체크), 서버 호출 없음. "다음"으로 다음 화면 이동.
3. **전화번호 인증**: `POST /auth/phone/send-code` → `POST /auth/phone/verify-code`로 `ticket`
   획득. **이 화면의 "다음"을 누르는 시점에 `POST /auth/signup`을 호출**(1~3단계에서 모은
   `loginId`/`password`/`phoneNumber`/`ticket`을 그대로 실어 보냄). 성공하면 계정이 생성되고
   **Access/Refresh Token이 그 자리에서 바로 발급된다** — 이 시점부터 클라이언트는 로그인된
   상태로 취급하고 토큰을 저장한다(이후 화면은 전부 이 토큰으로 인증된 요청).
   - 뒤로가기로 이 화면에 다시 돌아와도 "다음"이 signup을 또 호출하지 않도록, 이미 토큰을
     받은 상태면 그냥 다음 화면으로 넘어가야 한다(재요청 시 `USER_001`/`USER_002` 에러).
4. **이름**: 화면 진입 시 `GET /users/me`로 자동 생성된 기본 닉네임(`name`)을 프리필해서 보여준다.
   그대로 두고 "다음"을 누르면 아무 호출도 하지 않는다. 값을 바꾸면 `PATCH /users/me/name` 호출
   후 다음 화면으로.
5. **프로필 사진**: 업로드하면 `POST /files/profile-image/upload-url` → 응답의 `uploadUrl`로 R2에
   직접 `PUT` → `POST /files/profile-image/confirm`. 건너뛰면 아무 호출 없이 "완료".

### 왜 화면 순서가 보안에 영향 없는가
REST API는 프론트 화면 순서에 종속되지 않는다 — 공격자는 앱 UI를 거치지 않고 API를 직접,
임의 순서로 호출할 수 있다. 그래서 "전화번호 인증을 몇 번째에 두느냐"는 순수 UX 문제고, 실제
방어는 이미 API 레벨에 있다:
- SMS 스팸/문자폭탄: `AuthErrorCode.TOO_MANY_SMS_REQUESTS`(재발송 쿨다운),
  `TOO_MANY_VERIFICATION_ATTEMPTS`(인증 시도 5회 제한) — 전화번호 단위로 이미 제한됨.
- `signUpTicket` 탈취: `PhoneAuthService.verifyCode()`가 발급하는 `ticket`은 전화번호로 유추
  불가능한 `UUID.randomUUID()`이고, 해당 인증을 직접 완료한 호출자에게만 응답으로 반환된다.
  Redis에도 "이 전화번호가 인증됨" 같은 공개 플래그가 아니라 `ticket → phoneNumber`로 저장되므로,
  ticket 값 자체를 모르면 가로챌 수 없다(HTTPS 도청 등 전송 구간 공격은 순서와 무관한 별개 문제).
- `loginId` 동시 선점 경합: DB unique 제약 + 기존 `DataIntegrityViolationException → 409` 처리로
  이미 커버됨.

## 엔드포인트

### `POST /api/v1/auth/signup` (기존 엔드포인트 수정)
- 요청 DTO: `SignUpRequest`에서 `name` 필드 **제거**. 나머지(`loginId`, `password`,
  `phoneNumber`, `ticket`)는 변경 없음.
- **응답 DTO 변경**: `Void` → `TokenResponse`(`login`/`reissue`와 동일한 응답 스키마:
  `accessToken`, `refreshToken`, `accessTokenExpiresIn`). 가입 직후 클라이언트를 즉시 로그인
  상태로 만들어, 뒤이은 이름/프로필 사진 설정 화면을 별도 로그인 없이 인증된 API로 처리하기
  위함(위 "클라이언트 플로우" 참고).
- 실패 상태코드: 변경 없음(`AUTH_005`/`AUTH_006`/`USER_001`/`USER_002` 등 기존 그대로).
  `name` 관련 실패 케이스(`USER_003`)는 가입 시점에서 사라짐.
- 가입 처리 중 `name` 중복 검증 자체가 사라짐(클라이언트가 이름을 안 보내므로). 대신 내부적으로
  위 규칙에 따라 이름을 생성해 저장한다.
- 인증/권한 요구사항: 요청 자체는 비인증(변경 없음). 응답으로 토큰이 발급된다는 점만 추가.

### `GET /api/v1/users/me` (신규)
- 클라이언트가 로그인 직후 호출해서 "닉네임/프로필 사진이 아직 기본값인지"를 판단하고, 그렇다면
  UI에서 설정을 유도하기 위한 엔드포인트다(강제 차단은 하지 않음 — 위 "왜 강제 차단을 안 하는가"
  참고).
- 응답 DTO: `MyProfileResponse(name: String, nameCustomized: boolean, hasProfileImage: boolean)`
  - `nameCustomized`: `PATCH /api/v1/users/me/name`을 한 번이라도 성공적으로 호출했으면 `true`.
    닉네임 재계산-비교 방식은 쓸 수 없다(아래 "리스크" 참고).
  - `hasProfileImage`: `User.profileImageKey != null`
- 성공: `200 OK`
- 인증/권한 요구사항: Access Token 필요

### `PATCH /api/v1/users/me/name` (신규, `user` 도메인 최초 컨트롤러)
- 요청 DTO: `UpdateNameRequest(name: String)` — `@NotBlank @Size(max=20)`, 기존
  `SignUpRequest.name`/`/auth/name/check`와 동일한 제약(별도 문자 형식 제한은 없음, 기존과 동일).
- 응답 DTO: `ApiResponse<Void>` (성공 메시지만)
- 성공: `200 OK`
- 실패:
  - 이미 사용 중인 별명(자기 자신의 현재 이름은 예외) → `409 Conflict` +
    `UserErrorCode.NAME_ALREADY_EXISTS`(기존 에러코드 재사용)
- 인증/권한 요구사항: Access Token 필요(`@AuthenticationPrincipal UserPrincipal`)
- 기존 `GET /api/v1/auth/name/check`는 그대로 두고, 이제 가입 시점이 아니라 이 변경 화면에서
  "저장하기 전 미리 확인"용으로 쓰인다(엔드포인트 자체는 변경 없음).

### `POST /api/v1/files/profile-image/upload-url`, `/confirm` (기존 엔드포인트 동작 변경)
- 요청/응답 스키마, 상태코드 변경 없음.
- **인증 필요로 전환**: 지금은 `permitAll`이라 누구나 호출 가능한데, 실제 사용 시점이 "로그인
  이후 프로필 사진을 바꾸고 싶을 때"로 확정됐으므로 `@AuthenticationPrincipal UserPrincipal`을
  받도록 바꾼다.
- `upload-url`: `keyPrefix`를 하드코딩된 `"profile/temp"` 대신 `"profile/" + principal.userId()`로
  생성(기존 TODO "인증 붙으면 studentId로 교체" 해소).
- `confirm`: R2 존재 확인 후 `User.profileImageKey`에 실제로 저장(기존 TODO "Entity 생성 후
  연결할 것" 해소). `UserService`의 새 메서드(예: `updateProfileImage(userId, key)`)를 호출.

## 데이터 모델 변경
- `User.name`은 계속 `nullable=false, unique=true` 그대로 유지(항상 자동 생성값이 채워지므로
  nullable로 바꿀 필요가 없다 — 이전에 검토했던 "온보딩 강제 차단" 방향은 폐기됨).
- `User.profileImageKey`는 기존과 동일하게 nullable.
- **신규 컬럼 추가**: `User.nameCustomized`(`BOOLEAN NOT NULL DEFAULT FALSE`). 가입 시 항상
  `false`로 시작하고, `PATCH /api/v1/users/me/name`이 성공할 때 `true`로 바뀐다. `GET
  /api/v1/users/me`가 이 값을 그대로 노출한다.
- Flyway 마이그레이션 1개 필요: `V7__add_user_name_customized.sql`.

## 리스크 및 고려사항
- **학생 기본 닉네임 중복 불가능 근거**: 최종 숫자 접두사는 `zeroPad(grade,1) + zeroPad(classNo,1)
  + zeroPad(number,2)`로 **항상 정확히 4자리 고정 폭**이다(이 학교는 한 학년에 반이 4개뿐이라
  `classNo`가 2자리로 넘어갈 일이 없다). 고정 폭 문자열이므로 서로 다른 두 (grade, classNo,
  number) 조합이 같은 4자리 문자열을 만들려면 각 자리가 모두 일치해야 하고, 이는 결국 세 값이
  모두 같다는 뜻이라 `uq_class_slot` 제약과 모순된다. 따라서 숫자 접두사는 항상 유일하고, 그
  뒤에 어떤 이름이 붙어도 전체 문자열은 유일하다.
- **반이 4개를 넘는 학년이 생기면(향후 학교 규모 변경 등)**: `classNo`가 2자리(10 이상)로
  넘어가면 위 "고정 4자리" 전제가 깨진다. 지금 시점에는 반영하지 않고, 실제로 그런 변경이
  생기면 `classNo`도 2자리로 0채움하도록 코드를 바꿔야 한다는 점만 코드 주석으로 남겨둔다.
- **교사 랜덤코드 재시도**: 3자리(영숫자) 조합은 최대 5회 재시도로 사실상 항상 성공한다. 이론상
  5회 모두 실패하는 극희귀 케이스는 마지막 `save()`에서 DB unique 위반 →
  `DataIntegrityViolationException` → 기존 `GlobalExceptionHandler`가 `409`로 변환하는 경로로
  자연스럽게 흡수된다(신규 처리 불필요).
- **`file` 도메인 인증 전환**: 기존엔 `permitAll`이라 누구나 presigned URL을 발급받을 수
  있었는데, 이제 로그인 후 흐름으로 확정되어 인증을 요구해도 기능상 문제 없음. 다만 이 전환
  자체가 이번 이슈의 스코프 확장이라는 점을 명시(원 스캐폴드는 #1/#8 시절 프로토타입).
- **`user` 도메인 신설 위치 판단**: `isLoginIdAvailable`/`isNameAvailable`가 지금은
  관례상 `AuthService`(auth 도메인)에 있지만, "로그인한 내 정보를 바꾸는" 이번 API는 `user`
  도메인이 더 자연스럽다고 판단해 새 `UserController`/`UserService`를 만든다. 기존
  `AuthService`의 `isNameAvailable`(가입 전 중복확인용, `/auth/name/check`가 계속 사용)은
  그대로 두고, `UserService`는 "인증된 사용자 본인의 이름 변경"이라는 별도 관심사를 담당한다.
- **"기본값 여부"를 재계산-비교로 판단할 수 없는 이유**: 학생 기본 닉네임(학번+실명)은 결정적이라
  나중에 다시 계산해서 현재 값과 비교하는 방식도 가능하지만, 교사 기본 닉네임은 랜덤 구분자가
  들어가 재계산할 때마다 다른 문자열이 나온다 — 원래 발급됐던 값과 절대 다시 일치할 수 없다.
  두 타입을 동일한 방식으로 처리해야 하므로, 재계산-비교 대신 명시적 `nameCustomized` 플래그를
  별도로 저장하고 변경 API가 성공할 때만 갱신하는 방식을 택한다.
- **왜 강제 차단을 안 하는가**: 논의 초반엔 "닉네임/사진 미설정 시 다른 API 차단"(서버 강제)도
  검토했으나, JWT claim 추가·인가 필터·`User.name` nullable 마이그레이션까지 필요한 큰 변경이라
  폐기했다. 대신 항상 유효한 기본값(학번+실명 / `T-`+실명)을 자동으로 채워 넣어 "미완성 계정"
  상태 자체가 존재하지 않게 하고, `GET /users/me`의 `nameCustomized`/`hasProfileImage`는 순수
  UI 유도용 신호일 뿐 접근 제어에는 쓰이지 않는다.
- **가입 응답에 토큰을 바로 실어 보내는 것의 트레이드오프**: 이름/사진 화면까지 하나의 마법사
  흐름처럼 보이게 하려고 `signup` 성공 즉시 로그인 토큰을 발급한다. 사용자가 이름/사진 화면
  이전에 이탈해도 계정 자체는 이미 완결된 상태(기본값 보유)라 문제 없다. 클라이언트는 "비밀번호"
  화면으로 뒤로가기 후 재차 "다음"을 누르는 경우, 이미 토큰을 받았다면 `signup`을 재호출하지
  않고 다음 화면으로 넘어가도록 처리해야 한다(안 그러면 `ALREADY_REGISTERED`/
  `LOGIN_ID_ALREADY_EXISTS` 에러를 받는다).
