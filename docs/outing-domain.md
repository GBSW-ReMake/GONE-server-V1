# 외출(Outing) 도메인 — 기능 기획서 (초안, 이슈 생성 전)

> 아직 GitHub 이슈를 만들지 않은 상태의 초안이다. 이 문서 내용이 확정되면 이슈를 만들고,
> 문서명을 `docs/{이슈번호}-outing-{제목}.md` 규칙에 맞게 옮긴다.

## 개요/목적
평일 정해진 시간대(점심/저녁 등)에 외출을 신청 → 담당 선생님 승인(사인) → **학생 본인이
출발/도착 버튼으로 직접 보고**하는 흐름을 서버가 추적한다. 지금은 이 과정이 종이 외출증 +
선도부가 정문에서 수동으로 확인하고 카톡방에 나감/들어옴을 공유하는 방식으로 돌아가는데,
이 기획의 핵심은 **그 수동 확인/공유를 대체할 수 있을 만큼 "지금 누가 외출 중인지, 어디
있는지, 오늘 무슨 일이 있었는지"를 실시간으로 조회 가능하게 만드는 것**이다(요청하신
**"가시성" 중점** 요구사항) — 선도부는 더 이상 정문에서 학생을 직접 막아 확인하지 않고,
담당 선생님과 함께 **지켜보는 쪽(조회 권한)** 으로 역할이 바뀐다. 상태 추적뿐 아니라 외출 중
위치/동선까지 볼 수 있어야 한다.

## 용어 정리
- **외출증(Outing)**: 사유, 날짜, 시간대, 담당 선생님 서명 여부, 출발/도착 여부를 담은 한 건의
  외출 요청/기록.
- **선도부**: 이 프로젝트에 이미 있는 `Role` 코드 중 `DISCIPLINE`(`V6__add_role_and_user_role.sql`
  시드 데이터 확인 완료). **더 이상 출발/도착을 직접 확인하는 주체가 아니라, 현황을 지켜보는
  조회 권한을 가진 역할**이다(아래 참고).
- **담당 선생님**: 학생이 외출증을 신청할 때 "누구에게 사인받을지" 직접 지정하는 선생님 1명.
- **시간대(timeSlot)**: 외출이 허용되는 프리셋 구간(점심/저녁 등). 학생이 시각을 직접 입력하지
  않고 이 중에서 고른다.
- **출발/도착**: 선도부의 확인 없이 **학생 본인이 직접 "출발" 버튼(나갈 때)과 "도착"
  버튼(들어올 때)을 눌러 자기 신고(self-report)한다.** 담당 선생님/선도부는 이 신고 + 위치
  데이터를 보고 상황을 파악하는 쪽이다.

## 정책 가정 (확정 전 — 리뷰 시 조율 필요)
- **외출증은 공적 문서라, 서비스 닉네임/프로필 사진에 더해 실명 + 학년/반을 별도로 같이
  담는다.** 닉네임/사진을 빼는 게 아니라 "둘 다" 보여준다 — 앱 화면에서는 평소처럼
  닉네임/사진으로 보여주되, 외출증이라는 공적 문서 성격상 실제 신원(실명/학년/반)도 옆에
  명시돼 있어야 한다는 요구사항. 이 프로젝트는 `User.name`(서비스 닉네임)과
  `Gbsw.name`(학교 명단 원본 실명)을 이미 별개 개념으로 분리해두고 있다(`User.java` 주석
  확인) — 그 구분을 그대로 활용한다. 학생 쪽 응답 필드:
  - `studentNickname` — `User.name`(별명)
  - `studentProfileImageUrl` — `User.profileImageKey`가 있으면
    `R2FileService.generateDownloadUrl(key)`(기존 메서드, 신규 아님)로 만든 presigned
    URL, 없으면 `null`
  - `studentRealName` — `Gbsw.name`(실명, 공적 문서용)
  - `studentGrade` / `studentClassNo` — `Gbsw.grade`/`Gbsw.classNo`
  선생님은 승인 주체일 뿐이라 실명(`teacherName`, `Gbsw.name`)만 표시하고 닉네임/사진은
  담지 않는다 — 필요하면 리뷰 시 알려달라.
- **출발/도착은 선도부 확인 없이 학생 본인이 직접 버튼으로 보고하되, 그 순간의 GPS 좌표를
  같이 받아 학교 반경 안에 있을 때만 성립하도록 실시간 검증한다** (4/5번 엔드포인트). 선도부가
  하던 물리적 확인을 위치 기반 검증으로 대체하는 셈이다. 완전히 막을 수는 없다(GPS 위치 모킹
  같은 우회 수단은 존재) — 하지만 정상적인 사용에서 발생할 수 있는 실수나 무단이탈은 이
  수준으로 충분히 걸러진다고 판단했다. 학교의 정확한 좌표/허용 반경(가정: 200m, 아래 "아직
  결정 안 된 것" 참고)은 확인이 필요하다.
- **저녁 시간대(`DINNER`)는 18:10~21:10으로 반영**했다 — "점심시간은 6:10~9:10까지야"라고
  주신 시각이 점심(12시대)과는 안 맞고 저녁 자율학습 시간대(18~21시)와 맞아떨어져서, 저녁
  시간대 답변으로 이해하고 반영했다. 혹시 다른 의도였다면 알려달라.
- **신청 가능한 날짜 범위는 "오늘부터 이번 주 금요일까지"** (지난 날짜는 신청 불가, 다음 주는
  아직 신청 불가)로 확정했다.
- **신청 마감은 "그 신청 건의 시간대가 시작하기 전까지"** 로 일반화했다 — 원래 "12:30까지"라고
  하신 건 시간대가 점심 하나뿐이던 전제였고, 시간대가 여러 개(점심/저녁)로 늘어나면서
  "각 시간대 시작 시각 전까지"로 자연스럽게 일반화된다고 해석했다.
- **담당 선생님은 학생이 신청 시 직접 지정**한다(선생님 목록 중 택1). 이 프로젝트에는 아직
  "담임"/"교사-학생" 매핑 테이블이 없어서다(마이그레이션/엔티티 전체 확인 완료, 담임 개념을
  새로 만드는 건 이 기획 범위 밖).
- **같은 "날짜 + 시간대" 조합으로 진행 중인 외출증이 있으면 중복 신청 불가**, 그 외에는 하루에
  여러 건(예: 점심 한 번, 저녁 한 번) 신청 가능.
- **위치 핑(ping) 전송 주기는 30초~1분 간격으로 가정**했다(학생 앱이 외출 중에 주기적으로
  서버에 좌표를 보내는 방식). 실시간 지도로 보여주는 프론트 UI 자체는 이번 기획 범위 밖 —
  서버는 좌표 시계열 데이터를 저장/제공하는 역할까지만 한다.
- **역할(Role) 기반 인가를 이 프로젝트에서 처음 실제로 사용**하게 된다 — `Role`/`UserRole`
  테이블과 JWT `roles` 클레임까지는 이미 있지만(`#15`), 실제로 `hasRole(...)` 권한 체크를
  쓰는 코드는 아직 없다. 이 기획에서 `TEACHER`/`DISCIPLINE`/`STUDENT` 역할을 실제로 검사하는
  첫 사례가 된다(아래 "권한 모델" 참고).

## 권한 모델
- Access Token에는 이미 `roles` 클레임이 있고, `JwtAuthenticationFilter`가 이를
  `SimpleGrantedAuthority("ROLE_" + code)`로 변환해 `Authentication`에 올려둔다(기존 인프라,
  변경 없음). 다만 지금은 이 권한 정보를 실제로 검사하는 코드가 없다.
- 이번 기획에서 컨트롤러 메서드에 `@PreAuthorize("hasRole('TEACHER')")` 같은 애노테이션을
  붙여 역할별 접근을 제한할 것을 제안한다. 이를 쓰려면 `SecurityConfig`(또는 별도
  `@Configuration`)에 `@EnableMethodSecurity`를 한 번 추가해야 한다(현재 없음 — 이 기획의
  선행 작업).
- 엔드포인트별 필요 역할:
  1. 신청: `STUDENT`
  2. 승인/거절: `TEACHER` + 본인이 그 외출증에 지정된 담당 선생님인지 소유권 확인(역할만으로는
     부족 — 안 그러면 아무 선생님이나 남의 반 학생 외출증에 사인할 수 있다. `FileController`의
     프로필 이미지 소유권 확인과 같은 패턴)
  3. 출발/도착 보고: `STUDENT` + 본인 외출증인지 소유권 확인(더 이상 `DISCIPLINE`이 아님 —
     학생 본인이 직접 보고)
  4. 상태 목록 조회(누가 나갔는지, 위치 제외): `DISCIPLINE`, `TEACHER`, `ADMIN` 중 하나
  5. **위치/동선 조회: 그 외출증에 지정된 담당 선생님 본인 + `DISCIPLINE`만** — 전체 교사가
     아니라 딱 이 둘로 좁힌다(위치 데이터는 상태보다 민감한 정보라 접근을 더 좁게 둔다)

> ⚠️ **트레이드오프**: `@PreAuthorize`는 "역할이 있는지"까지만 선언적으로 표현할 수 있고,
> "이 특정 리소스의 소유자/담당자인지"(2, 3, 5번)는 SpEL로 억지로 표현하는 것보다 서비스
> 메서드 안에서 명시적으로 `if` 체크하는 게 더 읽기 쉽고 실수하기 어렵다. 그래서 이 기획에서는
> **역할 체크는 `@PreAuthorize`, 소유권 체크는 서비스 코드**로 역할을 나눈다.

## 도메인 모델

### 외부 식별자 정책 — `id`(내부) vs `code`(외부, 프론트 표시용)
> 외출증마다 프론트엔드 화면에 표시할 고유 코드를 둔다. DB 내부 자동증가 `id`(BIGINT PK)는
> FK 관계 등 내부용으로만 쓰고, **API가 주고받는 모든 `id` 필드와 경로 변수의 값은 실제로는
> 이 코드 값이다** — 이후 모든 엔드포인트 설명에서 경로의 `{id}`/응답의 `id`라고 쓴 것은 이
> 코드를 가리킨다(내부 PK를 그대로 노출하지 않는다).

- **형식**: 영숫자(대소문자 + 숫자) 10자리, 예: `8A1zx9202`
- **생성**: `SecureRandom` 기반 랜덤 문자열 생성 유틸(`OutingCodeGenerator`, 가칭) — 신청
  저장 시 생성해 `code` 컬럼(`VARCHAR(10)`, UNIQUE)에 저장. 충돌 시(확률상 거의 없지만) DB
  유니크 제약 위반을 잡아 재생성 후 재시도(최대 5회).
- **조회**: 서비스는 항상 `outingRepository.findByCode(code)`로 조회한다. `findById`(내부
  PK)는 리포지토리 내부/FK 조인 용도로만 남긴다.
- **왜 분리하나**: 정수 PK를 그대로 노출하면(`id=502`) "오늘 전체 몇 건 신청됐는지" 같은
  내부 규모 정보가 새어나가고 다음 값 추측도 쉬워진다. 이미 소유권 검증이 있어 보안상
  필수는 아니지만, 굳이 흘릴 이유가 없다는 관점의 추가 방어 + 프론트에 보여줄 "외출증
  번호"가 필요하다는 요구사항을 동시에 만족시킨다.

### `OutingProperties` (`@ConfigurationProperties(prefix = "outing")`, 신규)
학교 반경 위치 검증에 필요한 설정값. `NeisProperties`(학교 코드)와 같은 패턴 — 이 서버가 결국
한 학교 전용이라 값 하나로 고정, 로컬 `application-dev.yml`(git 미포함)에 실제 값을 둔다.
- `schoolLatitude` / `schoolLongitude` — 학교 기준 좌표(정확한 값 확인 필요)
- `schoolRadiusMeters` — 출발/도착이 유효하다고 인정할 반경(가정: `200`m, 실제 캠퍼스
  크기에 맞게 조정 필요)

### `OutingTimeSlot` (enum, 프리셋 + 커스텀)
기존 `meal` 도메인의 `MealType`(조식/중식/석식 프리셋)과 같은 패턴이되, 프리셋 외에 학생이
직접 시간을 정하는 경우도 지원한다.
1. `LUNCH` — 12:30~13:40 (서버가 시작/종료 시각을 채움, 클라이언트 입력 불가)
2. `DINNER` — 18:10~21:10 (위와 동일)
3. `CUSTOM` — 학생이 `customStartTime`/`customEndTime`을 직접 입력. 아래 제약 적용:
   - **허용 범위**: `08:30 ~ 21:10`(학교 있는 시간) 안에 있어야 함 — `customStartTime >=
     08:30`, `customEndTime <= 21:10`, `customEndTime > customStartTime`
   - **지속시간 제한 없음** — 위 범위 안이기만 하면 몇 시간짜리든 허용(예: 09:00~20:00도
     가능)
   - 이 범위는 `OutingPolicy.CUSTOM_WINDOW_START`(`08:30`)/`CUSTOM_WINDOW_END`(`21:10`)
     상수로 관리(가칭) — `DINNER` 종료 시각과 상한을 맞춰서 "저녁 자율학습 시간 이후 불가"
     정책과 일관되게 유지

> 💡 `LUNCH`/`DINNER`는 여전히 서버가 시간을 채우는 신뢰 경계 안쪽 값이고, `CUSTOM`만
> 클라이언트가 직접 값을 주는 예외라는 게 핵심 차이다. 검증(Bean Validation + 서비스 로직)은
> `CUSTOM`일 때만 `customStartTime`/`customEndTime` 필수, 그 외엔 무시(또는 요청에 있어도
> 서버가 프리셋 값으로 덮어씀).

### `Outing` 엔티티 (`outing` 테이블, 신규)
- `id` — 내부 PK(BIGINT, 자동증가), 외부에 노출하지 않음
- `code` — 외부 식별자(위 "외부 식별자 정책" 참고), `VARCHAR(10)` UNIQUE
- `student_user_id` — 신청한 학생(`User` FK)
- `teacher_user_id` — 신청 시 지정한 담당 선생님(`User` FK)
- `reason` — 사유(텍스트)
- `outing_date` — 외출 날짜(오늘~이번 주 금요일 중 하나)
- `time_slot` — `OutingTimeSlot`(`LUNCH`/`DINNER`/`CUSTOM`)
- `start_time` / `end_time` — `LUNCH`/`DINNER`면 서버가 프리셋 값으로 채움(클라이언트 직접
  입력 불가), `CUSTOM`이면 클라이언트가 보낸 `customStartTime`/`customEndTime`을 검증
  (08:30~21:10 범위, `end > start`) 후 그대로 저장
- `status` — 아래 `OutingStatus` 참고
- `approved_at` — 선생님이 승인/거절한 시각
- `rejected_reason` — 거절 시에만
- `departed_at` — **학생 본인**이 "출발" 버튼을 누른 시각
- `returned_at` — **학생 본인**이 "도착" 버튼을 누른 시각
- `created_at`
- 인덱스: `(student_user_id, outing_date, time_slot)` — 중복 신청 체크/본인 조회 모두 이
  조합으로 조회하므로 복합 인덱스 필요

> 💡 `departed_by`/`returned_by` 같은 "누가 확인했는지" 컬럼은 따로 두지 않는다 — 이제
> 확인 주체가 언제나 `student_user_id` 본인이라 별도 컬럼이 항상 같은 값을 중복 저장하는
> 꼴이 된다.

### `OutingStatus` (enum)
- `PENDING` — 신청됨, 선생님 서명 대기
- `APPROVED` — 선생님 서명 완료, 아직 출발 전
- `REJECTED` — 선생님이 거절(종료 상태)
- `DEPARTED` — 학생이 "출발" 버튼을 눌러 외출 중
- `RETURNED` — 학생이 "도착" 버튼을 눌러 종료(종료 상태)

### `OutingLocation` 엔티티 (`outing_location` 테이블, 신규) — 위치/동선 추적
- `id`
- `outing_id` — 어느 외출증에 대한 위치인지(`Outing` FK)
- `latitude` / `longitude`
- `recorded_at` — **서버가 수신한 시각**(클라이언트가 보낸 시각을 그대로 믿지 않는다 — 아래
  10번 엔드포인트의 주의사항 참고)
- 외출 하나당 여러 행(시계열) — `DEPARTED` 상태인 동안 학생 앱이 주기적으로 쌓고, `RETURNED`
  이후에도 지우지 않아 "종료 후 동선 조회"가 가능하게 한다.
- 인덱스: `(outing_id, recorded_at)` — 동선을 시간순으로 뽑는 조회 패턴에 필수

### 상태 전이
```
PENDING --(선생님 승인)--> APPROVED --(학생, 출발 버튼)--> DEPARTED --(학생, 도착 버튼)--> RETURNED
   |
   +--(선생님 거절)--> REJECTED
```
- `APPROVED`가 아닌 상태에서 출발 보고, `DEPARTED`가 아닌 상태에서 도착 보고 → 에러
- 한번 `REJECTED`/`RETURNED`가 되면 그 외출증은 더 이상 바뀌지 않는다(재신청은 새 레코드로)
- 위치 핑은 `DEPARTED` 상태일 때만 받는다(출발 전/도착 후 위치는 의미 없음)

### 1. `POST /api/v1/outings` — 외출증 신청
**권한**: `STUDENT`

**요청** (프리셋)
```json
{
  "reason": "치과 진료",
  "outingDate": "20260814",
  "timeSlot": "LUNCH",
  "teacherUserId": 42
}
```

**요청** (커스텀 — `timeSlot: "CUSTOM"`일 때만 `customStartTime`/`customEndTime` 필요)
```json
{
  "reason": "치과 진료",
  "outingDate": "20260814",
  "timeSlot": "CUSTOM",
  "customStartTime": "14:00",
  "customEndTime": "16:00",
  "teacherUserId": 42
}
```

**응답** (`201 Created`)
```json
{
  "success": true,
  "data": {
    "id": "8A1zx9202",
    "studentNickname": "길동이",
    "studentProfileImageUrl": "https://.../profile/1/abc.jpg?X-Amz-...",
    "studentRealName": "홍길동",
    "studentGrade": 3,
    "studentClassNo": 4,
    "teacherName": "김선생",
    "reason": "치과 진료",
    "outingDate": "20260814",
    "timeSlot": "LUNCH",
    "startTime": "12:30",
    "endTime": "13:40",
    "status": "PENDING"
  },
  "message": "외출증 신청이 접수되었습니다.",
  "code": null
}
```

**구현 로직**
1. `@AuthenticationPrincipal`에서 `studentUserId` 추출 후
   `UserRoleRepository.findRoleCodesByUserId(studentUserId)`로 `STUDENT` 역할 보유 확인 →
   없으면 거부(이 프로젝트에 아직 `@PreAuthorize`/`@EnableMethodSecurity` 인프라가 없어서,
   교사 역할 확인(6번)과 같은 방식으로 서비스 코드에서 직접 검사한다)
2. Bean Validation: `reason` not blank, `outingDate` 파싱 가능, `timeSlot` enum 값 유효.
   `timeSlot == CUSTOM`이면 `customStartTime`/`customEndTime` 필수(그 외 값이면 두 필드는
   무시)
3. 날짜 범위 검증: `outingDate < 오늘(KST)` 이거나 `오늘이 속한 주의 금요일`을 넘으면 거부
   (`LocalDate.now(KST).with(DayOfWeek.FRIDAY)`로 이번 주 금요일 계산)
4. 시작/종료 시각 확정:
   - `LUNCH`/`DINNER`: 서버가 프리셋 값으로 채움
   - `CUSTOM`: `customStartTime >= 08:30`, `customEndTime <= 21:10`,
     `customEndTime > customStartTime` 검증 → 벗어나면 거부
5. 마감 시각 검증: `outingDate == 오늘`이면서 `현재시각 >= (확정된) startTime`이면 거부
6. `UserRoleRepository.findRoleCodesByUserId(teacherUserId)`로 `TEACHER` 포함 여부 확인 →
   없으면 거부
7. **`userRepository.findByIdForUpdate(studentUserId)`로 그 학생의 `User` 행에 배타적 락**
   (`SELECT ... FOR UPDATE`, `@Lock(LockModeType.PESSIMISTIC_WRITE)`) — 이 메서드를 감싼
   서비스 메서드는 `@Transactional`이어야 하며, 이 지점부터 저장까지 같은 학생의 동시 요청은
   직렬화된다(아래 "동시성 처리" 참고)
8. 겹침 확인: 락을 잡은 채로 `(studentUserId, outingDate)`의 활성(`PENDING`/`APPROVED`/
   `DEPARTED`) 외출증을 조회해, 확정된 `[startTime, endTime)` 구간이 하나라도 겹치면 거부
   (프리셋끼리든 프리셋-커스텀이든 실제 시간 겹침 여부로 판단 — 순수 함수
   `OutingTimeUtils.overlaps(start1, end1, start2, end2)`로 분리)
9. `OutingCodeGenerator`로 `code` 생성(영숫자 10자리) 후 `Outing` 저장(`PENDING`) — `code`
   유니크 제약 위반 시(확률상 희박) 재생성 후 재시도(최대 5회)
10. 응답 DTO 변환:
    - `id = outing.getCode()`(내부 PK가 아니라 위에서 생성한 코드를 응답의 `id`로 사용)
    - `studentNickname = student.getName()`, `studentProfileImageUrl =
      student.getProfileImageKey() != null ? r2FileService.generateDownloadUrl(key) : null`
    - `studentRealName = student.getGbsw().getName()`, `studentGrade =
      student.getGbsw().getGrade()`, `studentClassNo = student.getGbsw().getClassNo()`
    - `teacherName = teacher.getGbsw().getName()`
    (위 "정책 가정" 참고 — 닉네임/사진은 `User`, 실명/학년/반은 `Gbsw`에서 따로 가져온다)

**에러**
- `outingDate`가 과거이거나 이번 주 범위를 벗어남(다음 주 이후 등) → `400` `OUTING_001`
- `outingDate`가 오늘인데 이미 확정된 `startTime`이 지남 → `400` `OUTING_001`(같은 코드,
  메시지로 구분)
- `CUSTOM`인데 `customStartTime`/`customEndTime`이 08:30~21:10 범위 밖이거나 `end <= start`
  → `400` `OUTING_011`
- `teacherUserId`가 `TEACHER` 역할이 아님 → `400` `OUTING_002`
- 그날 다른 활성 외출증과 시간이 겹침(프리셋끼리든 커스텀이 섞였든) → `409` `OUTING_003`
- 호출자가 `STUDENT` 역할이 아님 → `403` `OUTING_012`

> ⚠️ **동시성 처리 (확정)**: 겹침 확인(8번)과 저장(9번) 사이에는 시간차가 있어 같은 학생이
> 이중 클릭이나 서로 다른 시간대(프리셋/커스텀)를 거의 동시에 신청하면 두 요청 모두 겹침
> 확인을 통과해 중복 저장될 수 있다(check-then-act 레이스). 두 겹으로 막는다:
> - **프론트엔드**: 신청 버튼 클릭 즉시 비활성화(debounce)로 같은 클라이언트에서의 실수성
>   중복 요청 자체를 줄인다(서버 구현 범위는 아니지만 프론트 구현 전제로 명시).
> - **서버(행 락, 최종 방어선)**: "겹침 여부"는 두 값이 정확히 같은지가 아니라 **구간이
>   겹치는지**를 계산해야 하는 검사라, MySQL 유니크 인덱스로는 표현할 수 없다(PostgreSQL의
>   EXCLUDE 제약 같은 게 MySQL엔 없음). 대신 **그 학생의 `User` 행에 `SELECT ... FOR
>   UPDATE`로 배타적 락**을 걸어, 같은 학생의 신청 처리를 완전히 직렬화한다(다른 학생끼리는
>   서로 다른 행을 잠그므로 전혀 안 기다림):
>   ```java
>   public interface UserRepository extends JpaRepository<User, Long> {
>       @Lock(LockModeType.PESSIMISTIC_WRITE)
>       @Query("select u from User u where u.id = :id")
>       Optional<User> findByIdForUpdate(@Param("id") Long id);
>   }
>
>   @Transactional
>   public OutingResponse applyOuting(Long studentUserId, OutingApplyRequest request) {
>       userRepository.findByIdForUpdate(studentUserId).orElseThrow(...);   // 락 획득
>       // 이 시점부터 같은 학생의 동시 요청은 안전하게 직렬화됨 (7~9번)
>       ...
>   }   // 메서드 종료(커밋) 시 락 자동 해제
>   ```
>   먼저 락을 잡은 트랜잭션이 겹침 확인 + 저장 + 커밋을 마칠 때까지, 같은 학생의 다음
>   요청은 락 획득 지점에서 대기한다 — 대기가 풀리는 시점엔 이미 앞 트랜잭션이 커밋되어
>   있으므로, 겹침 확인이 항상 최신 상태 기준으로 정확하게 이뤄진다. 이 프로젝트에서
>   비관적 락(`PESSIMISTIC_WRITE`)을 쓰는 첫 사례라 `@EnableMethodSecurity`처럼 도입 자체가
>   선행 작업이다.
>
> 💡 **날짜 계산은 반드시 KST 기준**(`ZoneId.of("Asia/Seoul")`)으로 — 서버 기본 타임존에
> 의존하면 배포 환경이 바뀔 때 조용히 틀어질 수 있다(기존 `meal`/`timetable` 컨트롤러의
> `KST` 상수 패턴 재사용).

### 2. `PATCH /api/v1/outings/{code}/approve` — 선생님 승인
**권한**: `TEACHER` + 본인이 그 외출증의 `teacherUserId`와 일치

**요청**: 바디 없음(사인 = 승인 행위 자체)

**응답** (`200 OK`) — 1번의 응답과 같은 구조, `"status": "APPROVED"`

**구현 로직**
1. `code`로 `Outing` 조회(`findByCode`), 없으면 `404`
2. `principal.userId() == outing.getTeacherUserId()` 확인, 아니면 `403`
3. `outing.getStatus() == PENDING` 확인, 아니면 `409`
4. `status = APPROVED`, `approved_at = now` 로 갱신 후 저장

**에러**
- 본인이 지정된 선생님이 아님 → `403` `OUTING_004`
- 이미 승인/거절 처리된 건(`PENDING`이 아님) → `409` `OUTING_005`
- 존재하지 않는 `id` → `404` `OUTING_006`

> 💡 **멱등성 트레이드오프**: 이미 `APPROVED`인 걸 같은 선생님이 실수로 한 번 더 누르면
> 지금 설계는 `409`를 반환한다(재승인 성공 취급 안 함). "이미 승인됨"을 알려주는 게 사용자
> 입장에서 더 명확하다고 보고 이렇게 정했다 — 만약 프론트에서 이중 클릭 방지를 안 해도
> 괜찮게 하려면 멱등 처리(같은 상태면 그냥 `200` 반환)로 바꿀 수도 있다.

### 4. `POST /api/v1/outings/{code}/depart` — 출발 보고 (학생 본인)
**권한**: 그 외출증의 신청 학생 본인 (**선도부 확인 없음** — 학생이 직접 누른다, 대신 아래처럼
위치로 실시간 검증한다)

**요청** — 이 시점의 GPS 좌표를 함께 보낸다(선택 아님, 필수)
```json
{ "latitude": 36.1234, "longitude": 128.4321 }
```

**응답** (`200 OK`)
```json
{
  "success": true,
  "data": {
    "id": "8A1zx9202",
    "status": "DEPARTED",
    "departedAt": "2026-08-14T12:31:05"
  },
  "message": "출발이 기록되었습니다.",
  "code": null
}
```

**구현 로직**
1. `code`로 `Outing` 조회(`findByCode`), 없으면 `404`
2. `principal.userId() == outing.getStudentUserId()` 확인, 아니면 `403`
3. `status == APPROVED` 확인, 아니면 `409`(메시지로 "아직 승인 안 됨"/"이미 출발 처리됨" 등
   구분)
4. **위치 검증**: 요청으로 받은 좌표와 학교 기준 좌표(`OutingProperties.schoolLatitude`/
   `schoolLongitude`) 사이 거리를 하버사인(Haversine) 공식으로 계산 → 허용 반경
   (`OutingProperties.schoolRadiusMeters`)을 벗어나면 거부
5. `status = DEPARTED`, `departed_at = now`
6. 이 좌표를 `OutingLocation`의 첫 데이터포인트로 같이 저장(동선의 시작점이 자연스럽게
   "학교"가 되도록)

**에러**
- 본인 외출증이 아님 → `403` `OUTING_007`
- `APPROVED` 상태가 아닌데 출발 보고 시도 → `409` `OUTING_005`
- **학교 반경 밖에서 출발 보고 시도 → `400` `OUTING_010`**
- 존재하지 않는 `id` → `404` `OUTING_006`

> ✅ **자기 신고 한계를 위치 검증으로 좁힘**: 애초에 "실시간으로 막을 방법이 없다"고 썼던
> 부분을 다시 생각해보니, 위치를 사후 조회 용도로만 쓸 이유가 없었다 — **출발/도착 그 순간의
> 좌표를 요청에 실어 받으면, 그 자리에서 검증해서 아예 막을 수 있다.** 이제 학교 반경 밖에서는
> 출발/도착 자체가 성립하지 않는다.
>
> ⚠️ **그래도 완전히 막히는 건 아니다** — GPS 좌표는 위치 모킹 앱(특히 루팅/탈옥 기기)으로
> 조작 가능하다. "학교 안에 있는 척" 좌표를 보내고 실제로는 나가는 것까지는 이 검증으로 못
> 막는다. 다만 이 정도 부정 사용은 진입장벽이 꽤 있어서(일반 학생이 쉽게 할 수준은 아님),
> 이번 범위에서는 이 수준의 검증으로 충분하다고 본다 — 완벽한 방지보다 "정상적인 사용에서
> 실수/무단이탈을 자연스럽게 거른다"가 목표.

### 5. `POST /api/v1/outings/{code}/return` — 도착 보고 (학생 본인)
**권한**: 4번과 동일(본인 외출증)

**요청/응답**: 4번과 동일 구조(좌표 필수), `"status": "RETURNED"` + `returnedAt`

**구현 로직**: 4번과 동일하되 전이 조건이 `DEPARTED → RETURNED`, 위치 검증도 동일하게
적용(학교 반경 밖이면 "도착"이 성립하지 않는다 — 아직 학교에 도착 안 한 것이므로)

**에러**: 4번과 동일한 코드 체계, 상태 조건만 `DEPARTED`가 아니면 `409` `OUTING_005`,
학교 반경 밖이면 `400` `OUTING_010`

> 💡 도착 시점 위치를 마지막 `OutingLocation`으로 같이 저장해두면, 동선의 끝점도 자연스럽게
> "학교"로 남아 9번(동선 조회)의 데이터가 시작과 끝이 모두 학교인 완결된 경로가 된다.

### 6. `GET /api/v1/outings/me` — 본인 외출증 조회 (학생)
**권한**: `STUDENT`(본인 것만, `userId`는 토큰에서 추출 — 요청 파라미터로 안 받음)

**요청**: `date`(쿼리, 선택, `yyyyMMdd`, 기본값 오늘)

**응답** (`200 OK`) — `List<OutingResponse>` (그 날짜에 신청한 건 전부, 시간대별로 여러 건 가능)

**구현 로직**
1. `principal.userId()`와 `date`로 `outingRepository.findByStudentUserIdAndOutingDate(...)` 조회
2. DTO 리스트로 변환해 반환

> 💡 요청 파라미터로 `studentId`를 절대 받지 않는다 — 다른 학생 것을 조회하는 시도 자체가
> 구조적으로 불가능하게 만드는 게, 매번 소유권을 검사하는 것보다 안전하다(기존
> `UserController`/`TimetableController`와 같은 패턴). 학생 입장에서 이 화면이 곧 "출발/도착
> 버튼이 있는 그 화면"이 된다.

### 7. `GET /api/v1/outings/{code}` — 단건 상세 조회
**권한**: 신청 학생 본인, 지정된 담당 선생님, `DISCIPLINE`/`ADMIN` 중 하나

**구현 로직**
1. `code`로 `Outing` 조회(`findByCode`), 없으면 `404`
2. `principal.userId() == studentUserId`이거나 `== teacherUserId`이거나, 보유 역할에
   `DISCIPLINE`/`ADMIN`이 있으면 통과, 아니면 `403`
3. 응답 DTO 변환

**에러**: 위 권한에 해당 안 되는 사용자가 조회 시도 → `403` `OUTING_007`(IDOR 방지)

> ⚠️ 2번의 "역할 OR 소유권" 조건은 `@PreAuthorize`의 SpEL로도 표현 가능은 하지만
> (`hasRole('DISCIPLINE') or hasRole('ADMIN') or @outingAuth.isRelated(#id, principal)`),
> 조건이 복잡해질수록 애노테이션 한 줄에 로직을 욱여넣는 것보다 **서비스 메서드 안에서
> if로 명시적으로 검사**하는 편이 다음 사람이 읽고 고치기 쉽다 — 이 프로젝트의 권한 모델
> 원칙(위 참고)과 일관됨.

### 8. `GET /api/v1/outings/active` — 지금 외출 중인 학생 실시간 목록
> **🔭 가시성 핵심 ①** — 예전엔 선도부가 카톡방에 수동으로 공유하던 "누가 나갔고 아직
> 안 들어왔는지"를, 이제 학생이 직접 누른 출발/도착 신고를 실시간 조회로 대체하는
> 엔드포인트.

**권한**: `DISCIPLINE`, `TEACHER`, `ADMIN` 중 하나

**요청**: 파라미터 없음(항상 "지금 이 순간" 기준)

**응답** (`200 OK`)
```json
{
  "success": true,
  "data": [
    {
      "id": "8A1zx9202",
      "studentNickname": "길동이",
      "studentProfileImageUrl": "https://.../profile/1/abc.jpg?X-Amz-...",
      "studentRealName": "홍길동",
      "studentGrade": 3,
      "studentClassNo": 4,
      "reason": "치과 진료",
      "timeSlot": "LUNCH",
      "departedAt": "2026-08-14T12:31:05",
      "endTime": "13:40"
    }
  ],
  "message": "현재 외출 중인 학생 목록입니다.",
  "code": null
}
```

**구현 로직**
1. `outingRepository.findByStatus(DEPARTED)` 조회
2. DTO 리스트로 변환 반환 (위치 좌표는 포함하지 않음 — 9번에서 더 좁은 권한으로 별도 제공)

> ⚠️ **폴링 vs 실시간**: "실시간"을 표방하지만 실제로는 프론트가 이 엔드포인트를 주기적으로
> 다시 호출(폴링)하는 방식이 될 것이다. 학교 규모(선도부/선생님 몇 명이 보는 화면)에서는
> 10~30초 폴링으로 충분하지만, 진짜 실시간(초 단위)이 필요해지면 웹소켓/SSE 도입을 후속
> 과제로 고려해야 한다(이번 범위 밖).
>
> 💡 자정을 넘어도 `DEPARTED` 상태가 자동으로 정리되지 않는다 — 시간대 종료 시각을 넘겨도
> 도착 보고를 안 한 경우를 다루는 정책이 아직 없다(아래 "아직 결정 안 된 것" 참고). 예전엔
> 선도부가 사람이라 "얘 왜 아직도 안 들어왔지"를 눈치챌 수 있었지만, 이제 그 역할을 서버가
> 대신 챙겨야 한다 — 이 목록이 그 역할의 핵심.

### 9. `GET /api/v1/outings/{code}/locations` — 위치/동선 조회
> **🔭 가시성 핵심 ②** — 담당 선생님/선도부가 실시간 위치와 종료 후 동선을 보는 엔드포인트.
> 선도부의 물리적 확인이 없어진 만큼, 이 엔드포인트가 사실상 그 공백을 메우는 안전장치다.

**권한**: 그 외출증에 지정된 담당 선생님 본인, 또는 `DISCIPLINE` — 이 둘만(전체 교사 아님)

**응답** (`200 OK`)
```json
{
  "success": true,
  "data": {
    "outingId": 501,
    "status": "DEPARTED",
    "path": [
      { "latitude": 36.1234, "longitude": 128.4321, "recordedAt": "2026-08-14T12:31:30" },
      { "latitude": 36.1231, "longitude": 128.4325, "recordedAt": "2026-08-14T12:32:00" }
    ]
  },
  "message": "위치 조회에 성공했습니다.",
  "code": null
}
```

**구현 로직**
1. `code`로 `Outing` 조회(`findByCode`), 없으면 `404`
2. `principal.userId() == teacherUserId`이거나 보유 역할에 `DISCIPLINE`이 있으면 통과,
   아니면 `403`
3. `outingLocationRepository.findByOutingIdOrderByRecordedAtAsc(id)` 조회
4. `path` 리스트로 변환해 반환 — 외출이 아직 `DEPARTED`면 "실시간 위치"는 이 리스트의
   마지막 항목, 프론트가 이 엔드포인트를 주기적으로 다시 호출해 지도를 갱신한다. 종료
   (`RETURNED`) 후에는 전체 리스트가 곧 "그날의 동선"이 된다.

**에러**: 담당 선생님도 `DISCIPLINE`도 아닌 사용자가 조회 시도 → `403` `OUTING_008`

> 💡 시계열 데이터량은 크지 않다 — 30초 간격 기준 70분짜리 외출이면 약 140건. 인덱스
> (`outing_id`, `recorded_at`)만 있으면 페이지네이션 없이도 충분히 가볍다. 다만 핑 주기를
> 훨씬 촘촘하게 바꾸면(예: 5초) 재고할 필요가 있다.

### 10. `POST /api/v1/outings/{code}/locations` — 위치 핑 전송 (학생 앱)
**권한**: 그 외출증의 신청 학생 본인

**요청**
```json
{ "latitude": 36.1234, "longitude": 128.4321 }
```

**응답** (`200 OK`, 바디 최소화 — 매 핑마다 무거운 응답 불필요)
```json
{ "success": true, "data": null, "message": "위치가 저장되었습니다.", "code": null }
```

**구현 로직**
1. `code`로 `Outing` 조회(`findByCode`), 없으면 `404`
2. `principal.userId() == studentUserId` 확인, 아니면 `403`
3. `status == DEPARTED` 확인, 아니면 `409`
4. `latitude`/`longitude` 유효 범위 검증(`-90~90`, `-180~180`, Bean Validation)
5. `OutingLocation` 저장, `recorded_at`은 **서버가 수신한 시각으로 채움**

**에러**
- 본인 외출증이 아님 → `403` `OUTING_007`
- 그 외출증이 `DEPARTED` 상태가 아님(아직 출발 전이거나 이미 도착) → `409` `OUTING_009`

> ⚠️ **`recordedAt`을 클라이언트 시각 대신 서버 수신 시각으로 채우는 이유**: 클라이언트가
> 보내는 타임스탬프는 기기 시계 오차나 조작 가능성이 있다. 네트워크 지연으로 "실제 측정
> 순간"과 몇백 ms~수 초 어긋날 수 있지만, 이 정도 오차보다 "신뢰할 수 있는 값"이 더
> 중요하다고 판단했다.
>
> ⚠️ **위치 데이터는 개인정보다.** 저장 기간, 접근 로그(누가 언제 조회했는지), 삭제 정책이
> 필요하다 — 이번 기획에서는 다루지 않고 "아직 결정 안 된 것"에 남긴다.
>
> 💡 매 핑마다 `INSERT` 1건 — 학생 수·핑 빈도가 지금 학교 규모에서는 미미하지만, 나중에
> 부하가 실제로 문제가 되면 클라이언트 배치 전송(예: 1분치를 모아 한 번에 전송)이나 큐잉으로
> 최적화할 수 있다. 지금 단계에서 미리 최적화하지 않는다(YAGNI).

### 11. `GET /api/v1/outings?date=&status=` — 오늘 전체 현황 조회 (관리용 가시성)
**권한**: `DISCIPLINE`, `TEACHER`, `ADMIN`

**요청**: `date`(선택, 기본 오늘), `status`(선택, 특정 상태만 필터)

**구현 로직**
1. `date`(기본값 오늘) + `status`(선택)로 동적 조회
2. DTO 리스트로 변환해 반환

8번이 "지금 나가 있는 사람만" 보여준다면, 이건 "그날 신청된 것 전체"(대기/거절/완료 포함)를
보여줘서 하루치 전체 흐름을 한눈에 파악하게 한다.

> 💡 `date` 기본값을 반드시 "오늘"로 강제해야 한다 — 필터 없이 전체 기간을 다 뽑게 두면
> 나중에 데이터가 쌓였을 때 무제한 조회가 되어버린다. 인덱스는 `(outing_date, status)` 조합.

## 복귀 리마인더 (백그라운드 스케줄러)
> 요청하신 "도착했을 때 도착하셨나요? 알림을 지속적으로 보내서 누르게 하자"를 반영한
> 부분이다. REST 엔드포인트가 아니라 **서버가 주기적으로 스스로 도는 백그라운드 작업**이다.

### ⚠️ 선행 의존성: 이 프로젝트엔 푸시 알림 인프라가 아직 없다
학생 기기에 알림을 보내려면 FCM(Firebase Cloud Messaging) 같은 푸시 서비스 연동과, 사용자별
기기 토큰을 저장/관리하는 기능이 필요한데 지금 프로젝트엔 둘 다 없다. 이건 외출 도메인만의
문제가 아니라 앞으로 다른 기능(공지 등)에도 필요할 **공통 인프라**라, 이 문서 범위 안에서
전부 설계하기보다 별도 `notification` 공통 모듈 + 별도 이슈로 분리할 것을 제안한다. 여기서는
외출 도메인이 그 공통 모듈에 기대하는 "언제, 누구에게, 무슨 알림을 보낼지"만 정의한다.

### 스케줄러 로직
`OutingReminderScheduler`(가칭), `@Scheduled(fixedDelay = 1분)`로 주기 실행. 매 실행마다
`status = DEPARTED`인 모든 `Outing`을 순회하며 아래 조건을 검사한다.

1. **위치 기반 복귀 감지**: 그 외출증의 가장 최근 `OutingLocation`이 학교 반경 안이면 →
   학생에게 "도착하셨나요? '도착' 버튼을 눌러주세요" 알림 발송. 이후에도 계속
   `DEPARTED`로 남아있으면 5분 간격으로 재발송(가정값). 5번 엔드포인트(도착 보고)가
   호출되는 순간 그 `Outing`은 더 이상 이 조건에 안 걸리므로 자동으로 멈춘다.
2. **시간 초과 감지**: `현재시각 > end_time`인데 아직 `DEPARTED`면 →
   - 학생에게는 더 급한 문구("외출 시간이 지났습니다, 빨리 복귀해주세요")로 전환
   - **동시에 담당 선생님 + 선도부 전원에게도 알림**("OO 학생이 아직 복귀하지 않았습니다") —
     여기서부터는 순수 리마인더가 아니라 **사람의 개입이 필요한 상황으로 격상**한다. 이게
     사실 이 스케줄러의 진짜 존재 이유에 가깝다 — 예전엔 선도부가 사람이라 "쟤 왜 안
     들어오지"를 눈치챌 수 있었는데, 그 역할을 서버가 능동적으로 대신하는 것.

> ⚠️ **알림 상한이 필요하다**: 자정 넘어서까지 5분마다 알림이 계속 울리면 그 자체로 민폐다.
> 시간대 종료 후 일정 시간(가정: 3시간) 지나면 자동 알림은 멈추고, 그 뒤는 학교 측이
> 수동으로 대응하는 프로세스로 넘기는 게 맞다고 본다 — 서버가 무한정 알림을 보내는 건
> 오히려 신뢰를 깎아먹는다.

## 엣지케이스 정리
요청하신 대로 시간 초과/미확인 등의 예외 상황을 한곳에 모았다.

1. **위치는 학교 안인데 도착 버튼을 안 누름**
   → 위 스케줄러 조건 1번으로 알림 유도. 서버가 "도착했다"고 자동으로 상태를 바꿔주지는
   않는다(자기 신고 원칙 유지 — 위치는 어디까지나 신호일 뿐, 상태 전이는 항상 학생의 명시적
   버튼 클릭으로만 일어난다).

2. **시간대 종료 시각을 넘겼는데 아직 `DEPARTED`(무단 지각/미복귀)**
   → 스케줄러 조건 2번으로 학생 알림 강도 상승 + 담당 선생님/선도부에게 즉시 알림. 8번
   (`/active`) 목록에도 계속 남아있어 계속 눈에 띈다.

3. **도착 버튼을 눌렀는데 실제 위치가 학교 반경 밖 (`OUTING_010`)**
   → 이미 막히지만, 반경 경계 부근에서는 GPS 오차로 "분명 정문 앞인데 반경 밖으로 판정"되는
   상황이 생길 수 있다. 반경에 여유를 넉넉히 두거나(예: 실제 캠퍼스 크기 + 오차범위), 위치
   정확도(`accuracy`) 값도 같이 받아 오차가 너무 크면 "다시 시도해주세요" 안내를 하는 방식을
   고려할 수 있다(이번 범위에서 세부 구현까지는 안 함).

4. **위치 핑 자체가 끊김** (앱 백그라운드 종료, 배터리 절약 모드, 오프라인 등)
   → 서버는 "학교 반경 안으로 돌아왔는지" 판단할 근거(위치)가 없어 스케줄러 조건 1번이 아예
   발동하지 않는다. 이 경우 조건 2번(시간 초과)만이 유일한 안전망이 된다. 위치 핑이 일정
   시간(가정: 10분) 이상 끊긴 `DEPARTED` 건은 8/11번 목록에 "위치 추적 끊김" 같은 표시를
   추가해 사람이 더 빨리 알아채게 하는 것도 고려할 수 있다(후속 과제).

5. **학생이 알림을 못 받는 경우** (앱 삭제/로그아웃/알림 권한 꺼짐)
   → 서버는 발송 성공(FCM에 전달 성공) 여부까지만 알 수 있고, 학생이 실제로 봤는지는 알 방법이
   없다. 결국 최종 안전망은 여전히 **사람(담당 선생님/선도부)이 8/11번 목록을 보고 판단**하는
   것 — 이 스케줄러는 그 판단을 도와주는 보조 수단이지 완전한 자동화가 아니다.

6. **하루에 시간대를 여러 개 신청했을 때(점심+저녁), 저녁 외출 중 학교에 잠깐 들렀다 다시
   나가는 경우**
   → 도착 버튼을 누르면 그 외출증은 `RETURNED`로 종료된다. 다시 나가려면 새 외출증을
   신청해야 한다(이미 끝난 건은 재사용 불가) — 정책상 자연스러운 제약이지만, 학생 입장에서는
   "잠깐 들른 건데 왜 새로 신청해야 하지"로 헷갈릴 수 있어 프론트 안내 문구가 필요하다.

7. **자정을 넘겨도 복귀 안 함**
   → 위 "알림 상한"에 따라 일정 시간 뒤 자동 알림은 멈춘다. 그 이후 처리(생활지도 개입 등)는
   서버 범위 밖의 학교 행정 프로세스다.

8. **여러 선생님/선도부가 동시에 알림을 받는데 아무도 확인 안 함**
   → 알림 수신자가 실제로 확인했는지는 서버가 알 수 없다(5번과 같은 한계). 필요하면 나중에
   "확인함" 버튼으로 담당자를 명시적으로 지정하는 기능을 고려할 수 있으나 이번 범위 밖.

## 에러 코드 (`OutingErrorCode`, 신규 패키지 `outing`)
1. `OUTING_001` (400) — 신청 가능한 날짜/시간이 아닙니다
2. `OUTING_002` (400) — 지정한 선생님을 찾을 수 없습니다
3. `OUTING_003` (409) — 같은 날짜/시간대에 이미 진행 중인 외출증이 있습니다
4. `OUTING_004` (403) — 본인에게 지정된 외출증만 처리할 수 있습니다
5. `OUTING_005` (409) — 지금 상태에서는 처리할 수 없는 요청입니다(상태 전이 규칙 위반)
6. `OUTING_006` (404) — 외출증을 찾을 수 없습니다
7. `OUTING_007` (403) — 이 외출증에 접근할 권한이 없습니다
8. `OUTING_008` (403) — 위치 조회 권한이 없습니다(담당 선생님/선도부만 가능)
9. `OUTING_009` (409) — 지금은 위치를 기록할 수 없는 상태입니다(외출 중이 아님)
10. `OUTING_010` (400) — 학교 반경 밖에서는 출발/도착 처리를 할 수 없습니다
11. `OUTING_011` (400) — 커스텀 시간대는 08:30~21:10 범위 안이어야 합니다
12. `OUTING_012` (403) — 학생만 외출증을 신청할 수 있습니다

## 공통 구현 고려사항
- **`@EnableMethodSecurity` 도입이 이 기획의 진짜 선행 작업**이다 — 이게 없으면 위 모든
  `@PreAuthorize`가 그냥 무시된다(에러 없이 조용히 인가가 안 먹힘 → 심각한 보안 결함으로
  이어질 수 있으니 도입 후 반드시 "역할 없는 사용자가 실제로 403을 받는지" 통합 테스트로
  확인해야 한다).
- **소유권 체크 누락이 가장 위험한 실수 지점**이다(2, 3, 4, 5, 9, 10번) — 역할만 확인하고
  소유권을 빼먹으면 "아무 선생님이나 남의 학생 외출증에 사인", "아무 학생이나 남의 외출증
  출발/도착을 대신 누름", "아무 학생이나 남의 외출증에 위치 핑 전송" 같은 심각한 IDOR이
  생긴다. 이 엔드포인트들은 반드시 유닛 테스트에 "다른 사람 것에 접근 시도 → 403" 케이스를
  넣는다.
- **위치 기반 검증(하버사인 거리 계산)은 순수 함수로 별도 유틸에 분리**하는 게 좋다(예:
  `GeoUtils.distanceMeters(lat1, lng1, lat2, lng2)`) — 4/5번 엔드포인트 양쪽에서 재사용하고,
  경계값(정확히 반경 위/아래) 단위 테스트를 붙이기도 쉬워진다.
- **시간 관련 로직은 전부 KST 고정**(`ZoneId.of("Asia/Seoul")`) — 서버 배포 환경의 기본
  타임존에 의존하지 않는다.
- **동시성**: 신청(1번)의 겹침 체크만 진짜 레이스 컨디션 위험이 있고, 나머지(승인/거절/출발/
  도착)는 상태 전이 조건 자체가 자연스러운 락 역할을 한다(같은 상태에서만 다음 단계로 갈 수
  있으므로 두 번째 시도는 자동으로 막힘). 신청의 레이스는 프론트 더블클릭 방지 + 서버
  `User` 행 비관적 락(위 1번 엔드포인트 "동시성 처리" 참고, 확정)으로 방어한다.
- **외부 식별자**: 모든 조회/경로는 내부 `id`가 아니라 `code`로 한다(위 "외부 식별자 정책"
  참고) — 컨트롤러 파라미터 타입은 `String code`, 서비스는 `findByCode` 사용.

## 아직 결정 안 된 것 (리뷰 필요)
- **학교의 정확한 좌표(`schoolLatitude`/`schoolLongitude`)와 허용 반경(가정: 200m)** — 이
  값이 틀리면 정문 근처인데도 반경 밖으로 판정될 수 있어 정확도가 중요하다.
- 위치 핑 전송 주기(가정: 30초~1분) — 배터리/데이터 사용량과 실시간성의 절충점
- GPS 신호가 약한 상황(실내, 건물 밀집 지역)에서 반경 판정이 오작동할 가능성 — 여유
  반경을 넉넉히 두거나, 위치 정확도(accuracy) 값도 같이 받아 너무 부정확하면 재시도를
  요청하는 방식을 고려할 수 있음(이번 범위에서는 다루지 않음)
- 위치 데이터 보존 기간(무기한 저장할지, 일정 기간 후 삭제할지 — 개인정보 관점에서 정책 필요)
- **푸시 알림 인프라(FCM 등) 도입을 별도 이슈/공통 모듈로 분리할지, 이 이슈 안에 포함할지** —
  범위가 꽤 커서 분리를 제안했지만 최종 판단 필요
- 복귀 리마인더 재발송 간격(가정: 5분)과 발송 상한 시간(가정: 시간대 종료 후 3시간) — 실제
  운영해보고 조정 가능
- 위치 핑이 얼마나 끊겨야 "추적 끊김"으로 표시할지(가정: 10분)
