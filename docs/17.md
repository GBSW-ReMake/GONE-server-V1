# #17 로그인 ID 필드에 loginId/전화번호 겸용 입력 지원

관련 이슈: https://github.com/GBSW-ReMake/GONE-server-V1/issues/17

## 개요/목적
현재 `POST /api/v1/auth/login`은 `loginId` + `password`만으로 로그인한다. 사용자가 가입 시 만든
`loginId`를 잊어도 전화번호로 로그인할 수 있도록, 로그인 요청의 ID 필드에 `loginId` 또는
`phoneNumber` 중 아무 값이나 입력해도 인식하도록 개선한다.

엔드포인트/DTO 스키마 변경은 없다. 기존 로직(회원 조회 방식)만 수정한다.

## 변경 전/후 동작 차이

**변경 전**
- `LoginRequest.loginId`에 값을 넣으면 `UserDetailsServiceImpl.loadUserByUsername`이
  `userRepository.findByLoginId(loginId)`로만 조회한다 (`common/security/UserDetailsServiceImpl.java:27`).
- 전화번호를 입력하면 사용자를 찾지 못해 `UsernameNotFoundException` → `AuthenticationException`
  → `AuthErrorCode.INVALID_CREDENTIALS`로 처리된다 (사실상 로그인 실패).

**변경 후**
- 동일한 입력값으로 `loginId` 또는 `phoneNumber`와 일치하는 회원을 단일 쿼리로 조회한다.
- 일치하는 회원이 있으면 정상 로그인 플로우(비밀번호 검증 → JWT 발급)로 이어진다.
- 못 찾으면 기존과 동일하게 `AuthErrorCode.INVALID_CREDENTIALS`.

### 구현 방식
쿼리를 두 번 나눠 순차 조회(loginId 조회 후 없으면 phoneNumber 재조회)하지 않고, Spring Data JPA
derived query의 `Or` 조건으로 한 번에 조회한다.

```java
// UserRepository
Optional<User> findFirstByLoginIdOrPhoneNumber(String loginId, String phoneNumber);
```

```java
// UserDetailsServiceImpl.loadUserByUsername
User user = userRepository.findFirstByLoginIdOrPhoneNumber(identifier, identifier)
    .orElseThrow(() -> new UsernameNotFoundException(...));
```

- `WHERE login_id = ? OR phone_number = ?` 단일 쿼리로 실행되며, 두 컬럼 모두 unique 제약(=인덱스)이
  있어 성능 문제 없음. 기존 `findByLoginId`/`existsByLoginId` derived-query 컨벤션과도 일관된다.
- `findBy...` 대신 `findFirstBy...`를 쓴다: OR 조건에 일치하는 행이 우연히 2건(예: A의 loginId가
  B의 phoneNumber와 같은 문자열인 경우)이면 `findBy...`는 `IncorrectResultSizeDataAccessException`을
  던지지만, `findFirstBy...`는 예외 없이 1건만 받는다. 자세한 근거는 아래 리스크 항목 참고.
- 정규식으로 "이 입력값이 전화번호 형식인지 loginId 형식인지" 미리 판별해서 분기하는 방식은
  채택하지 않는다. `loginId` 패턴(`^[a-zA-Z0-9]{4,20}$`, `SignUpRequest.java`)이 숫자만으로
  구성된 값도 허용하므로, 패턴 기반 분기는 이론상 모호성이 남는다.
- `LoginRequest`의 필드명을 `loginId`에서 `identifier`로 변경한다 (API 계약 변경 — 요청 바디의
  키 이름이 `loginId` → `identifier`로 바뀜). loginId 또는 전화번호를 받는다는 의미를 필드명으로
  명확히 드러낸다.

## 엔드포인트
기존 `POST /api/v1/auth/login`을 그대로 사용한다 (경로/메서드 변경 없음).
- 요청 DTO: `LoginRequest` — **필드명 변경**: `loginId: String` → `identifier: String`
  (`password: String`은 변경 없음)
- 응답 DTO: 변경 없음
- 성공: `200 OK`
- 실패: `401 Unauthorized` + `AuthErrorCode.INVALID_CREDENTIALS` (AUTH_007) — 기존과 동일하게
  "회원 없음"과 "비밀번호 불일치"를 구분하지 않는다 (계정 존재 여부 노출 방지 정책 유지).
- 인증/권한 요구사항: 없음 (로그인 자체는 비인증 엔드포인트)

## 데이터 모델 변경
- 엔티티 필드 추가/변경 없음. `User.phoneNumber`는 이미 `nullable=false, unique=true`로 존재한다
  (`user/entity/User.java`, V2 마이그레이션에서부터 유니크 제약 있음).
- Flyway 마이그레이션 불필요.
- `UserRepository`에 조회 메서드만 추가: `Optional<User> findFirstByLoginIdOrPhoneNumber(String loginId, String phoneNumber)`
  (기존 `findByLoginId`와 동일한 derived-query 패턴, `First` 프리픽스만 추가).

## 리스크 및 고려사항
- **모호성 케이스 (2건 매칭)**: 어떤 회원 A의 `loginId`가 다른 회원 B의 `phoneNumber`와 우연히
  같은 문자열이면, `WHERE login_id = ? OR phone_number = ?` 조건에 두 회원이 모두 걸린다.
  `loginId`는 영숫자 4~20자 자유 형식(숫자만으로 구성 가능)이고 `phoneNumber`는 가입 시
  `^01[0-9]\d{7,8}$` 패턴을 거치므로 실질적 충돌 가능성은 낮지만, 0은 아니다.
  `findFirstBy...`를 사용해 이 경우에도 예외 없이 둘 중 한 명(정렬 기준 미지정 시 DB가 임의로
  고른 1건)만 반환하도록 한다. 비밀번호가 다르면 어차피 `INVALID_CREDENTIALS`로 안전하게
  실패하므로 보안 노출은 없다 — 다만 극히 드문 충돌 상황에서는 전화번호 소유자가 자신의 번호로
  로그인을 시도했는데 다른 사람이 매칭되어 실패하는 예상 못 한 UX가 있을 수 있다. 이 리스크는
  허용하고 별도 충돌 방지 로직(가입 시 loginId가 전화번호 형식과 겹치지 않도록 막는 등)은
  이번 이슈 범위 밖으로 둔다.
- **성능**: 단일 쿼리(`OR` 조건)이므로 기존 `findByLoginId` 1회 호출과 쿼리 횟수가 동일하다.
  두 컬럼 모두 unique 인덱스가 있어 문제 없음.
- **보안**: 기존과 동일하게 `INVALID_CREDENTIALS` 단일 에러로 응답하므로 계정 존재 여부/구분
  방식이 외부에 노출되지 않는다.
