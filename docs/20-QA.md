## QA — 실제 환경 검증

### 검증한 것 (실제 로컬 MySQL + Redis + 서버 기동)
이번엔 Redis가 로컬에 떠 있어서(#17 QA 때와 달리) 로그인 성공(200) 케이스까지 실서버로 끝까지
검증할 수 있었다.

- **학생 가입 전체 흐름**: `send-code` → `verify-code` → `signup`(학번 3-2-5, 실명 "QA학생")
  → 응답에 Access/Refresh Token이 바로 담겨 옴 확인. DB 확인 결과 `name = "3205QA학생"` — 번호
  한 자리(5)가 0채움되어 4자리 학번 형식이 정확히 생성됨을 확인.
- **교사 가입 전체 흐름**: 동일하게 진행, DB 확인 결과 `name = "T-118-QA교사"` — `T-{랜덤3자리}-{실명}`
  형식 정확히 생성됨을 확인.
- **인증 게이팅**: `GET /users/me`, `POST /files/profile-image/upload-url`을 토큰 없이 호출 →
  둘 다 `401 COMMON_002`로 정확히 차단됨을 확인. 토큰 포함 시 정상 응답.
- **`GET /users/me`**: 가입 직후 자동 생성된 이름과 `hasProfileImage: false`가 정확히 조회됨.
- **`PATCH /users/me/name`**: 별명 변경 성공, 이후 `GET /users/me`로 변경 반영 확인.
- **`upload-url`**: 실제 R2(remake-gone-dev 버킷)에 대해 presigned URL이 발급되고, `key`가
  `profile/{실제 userId}/...` 형식으로 만들어짐을 확인 — 기존 TODO("인증 붙으면 studentId로
  교체")가 실제로 해소됐음을 실환경에서 확인.
- **`confirm` 실패 경로**: 존재하지 않는 key로 호출 → `400 FILE_001` 정확히 응답.
- 테스트에 사용한 계정(`qastudent01`, `qateacher01`)과 임시로 추가한 `Gbsw` 명단 2건은 검증
  후 모두 삭제 완료(`user`, `user_role`, `gbsw` 테이블 확인 결과 잔여 데이터 없음).

### 검증하지 못한 것 (환경/시간 제약)
- **`confirm` 성공 경로의 완전한 실서버 왕복**: 실제로 R2에 바이트를 `PUT`한 뒤 `confirm`을
  호출해 `User.profileImageKey`가 저장되는 것까지는 실서버로 확인하지 않았다(R2에 실제 테스트
  파일을 남기고 지울 수단이 없어 범위를 좁힘). 대신 `FileControllerTest`(mock 기반)에서 "R2에
  존재 확인되면 `userService.updateProfileImage` 호출"을, `UserServiceTest`에서
  "`updateProfileImage`가 실제로 필드를 갱신하는지"를 각각 단위 테스트로 확인했다 — 두 테스트를
  이으면 전체 경로가 커버되지만, 진짜 R2 바이트 업로드까지 포함한 end-to-end는 아니다.

### 조사 중 발견한 이슈(이번 PR 범위 밖, 기존 코드)
QA 도중 `PATCH /users/me/name`에 한글 별명을 담아 호출했을 때 처음에 `500 COMMON_007`을
받아서 실제 버그인 줄 알았는데, 조사해보니 curl 호출 시 쉘(Git Bash) 인라인 문자열의 한글
인코딩이 깨져서 전달된 테스트 방법 문제였다(UTF-8 파일로 바디를 넘기니 정상 동작 확인).
다만 이 과정에서 `GlobalExceptionHandler.handleException`(폴백 500 핸들러)이 **예외를 전혀
로깅하지 않는다**는 걸 발견했다 — 그래서 실제 원인 파악에 시간이 걸렸다. 이번 이슈와 무관한
기존 코드이므로 고치지 않았지만, 원인 진단이 어려워지는 실질적인 문제라 기록해둔다(별도 이슈로
분리 제안).

## 코드 리뷰 (자체 점검)

### 확인한 항목 (문제 없음)
- 학생 기본 닉네임 유일성 근거(`docs/20.md` 리스크 섹션)를 실제 `uq_class_slot` 제약과 대조해
  다시 확인 — 고정 4자리 폭이라는 전제가 실제 스키마와 일치함.
- `AuthService`가 `file` 도메인에 직접 의존하지 않고, `UserService`를 통해서만 프로필 이미지를
  다룬다(계층 분리 유지).
- `SecurityConfig`의 `/api/v1/users/**` 매처가 지금 존재하는 두 엔드포인트(`GET /me`,
  `PATCH /me/name`) 외에 과도하게 넓게 막는 부분은 없음(현재 이 prefix 아래 다른 공개 API 없음).

### 이슈 없음
이번 조사에서는 심각도 있는 새 버그를 찾지 못했다.
