## 🟢 트러블 1 [85] `JwtAuthenticationFilter` 테스트 없음 + 거짓 주석 — ✅ 수정 완료

**문제**
`JwtProviderTest`, `RestAuthenticationEntryPointTest`는 추가했지만 정작 `JwtAuthenticationFilter`
자체(헤더 파싱, 토큰 검증 실패 시 조용히 통과시키는 분기)는 테스트가 없다. 게다가
`AuthControllerTest`의 `Logout` 중첩 클래스 주석은 "인증 필요 여부 자체(401 처리)는 ...
별도로 단위 테스트한다"고 적어놨는데, 그 별도 테스트가 실제로는 존재하지 않는다.

**왜 고쳐야 하는가**
- `docs/rules/test-convention.md`: "새 서비스/컨트롤러 로직을 추가하면 대응하는 테스트를 반드시
  함께 작성한다" 위반.
- `/logout`의 401 거부는 이 필터가 없으면 성립하지 않는 핵심 보안 로직인데 자동 커버리지가 0.
- 주석이 거짓이라 나중에 이 코드를 보는 사람(나 자신 포함)이 "테스트가 있다"고 오해하고 넘어감.

**해결 방안**
1. **`JwtAuthenticationFilter` 자체 단위 테스트 추가** (Mockito로 `HttpServletRequest`/
   `HttpServletResponse`/`FilterChain` 목킹, `doFilterInternal()` 직접 호출 후
   `SecurityContextHolder` 상태 검증)
   - 장점: 빠름, 외부 인프라/Spring 컨텍스트 불필요, "슬라이스 테스트가 Security 필터를 안
     태운다"는 이번에 확인된 문제와 무관하게 확실히 동작 검증 가능.
   - 단점: `SecurityConfig`에 실제로 필터가 등록되는지, 필터 순서가 맞는지까지는 검증 못 함.
2. **`@WebMvcTest` 슬라이스에서 검증**
   - 장점: 실제 필터 체인처럼 보임.
   - 단점: 이 프로젝트의 `@WebMvcTest`는 Security 필터 체인이 MockMvc에 실제로 안 붙는다
     (`addFilters` 값과 무관, 이번 조사에서 이미 확인됨) — **이미 실패가 확인된 방법**이라
     시간 낭비.
3. **서버 기동 + Postman/curl 수동 통합 확인 후 QA 문서에 기록**
   - 장점: 실제 필터 체인 전체(순서 포함)를 가장 정확하게 검증.
   - 단점: 자동화가 아니라 회귀 방지가 안 되고, 코드 바뀔 때마다 사람이 다시 해야 함.

**결정**: 1번 적용 완료 — `JwtAuthenticationFilterTest` 추가(헤더 없음/Bearer 접두사 없음/
정상 토큰/위조·만료 토큰 4가지 케이스), `AuthControllerTest`의 거짓 주석도 실제 테스트 위치를
가리키도록 수정.

## 🟠 트러블 2 [Medium] Refresh Token 재발급(rotation)의 read-then-write가 원자적이지 않음

**문제**
같은 Refresh Token으로 거의 동시에 두 개의 `/reissue` 요청이 오면, 둘 다
`redisRepository.find()`에서 같은(유효한) 값을 읽고 일치 검사를 통과한 뒤, 각자 새 토큰을
발급해 `redisRepository.save()`로 덮어쓴다. 나중에 쓴 요청이 이기므로, 먼저 응답을 받은
클라이언트의 새 Refresh Token은 이미 Redis에서 다른 값으로 대체되어 다음 재발급 시 즉시
거부된다.
- 위치: `src/main/java/com/remake/gone/auth/service/AuthService.java:149` (`reissue` 메서드)
- 2차 리뷰(코드 주석 정합성 담당 에이전트)에서도 독립적으로 재확인: `GlobalExceptionHandler`가
  DB unique 제약의 check-then-act 레이스를 "DB가 원자적으로 해결해준다"고 설명하는 것과 달리,
  Redis `SET`은 그런 보장이 없어 이 레이스는 아무도 안 막아준다.

**왜 고쳐야 하는가**
- 실제 보안 침해는 아니다(탈취범이 이득을 보진 않음). 하지만 정상 사용자가 드물게 예기치 않은
  재로그인을 겪을 수 있다.

**해결 방안**
1. **지금은 그대로 두고 주석으로만 한계를 남긴다**
   - 장점: 추가 구현 불필요. 동시 요청이 드문 일반 사용 패턴에서는 영향이 작음.
   - 단점: 근본 원인은 안 고쳐짐.
2. **Redis 원자적 연산(Lua 스크립트로 compare-and-set)으로 rotation을 원자화**
   - 장점: 레이스 자체를 제거.
   - 단점: Lua 스크립트 관리/테스트 비용 추가, 이번 이슈 범위 대비 과함.

**제안**: 1번(보류) — 이번 범위에서는 두고, 실제로 동시 재발급 이슈가 리포트되면 그때 2번 적용.

## 🟢 트러블 3 [75] `TokenResponse` 통합이 기획서에 반영 안 됨 — ✅ 수정 완료

**문제**
`docs/10.md`는 로그인/재발급 응답으로 `LoginResponse`/`ReissueResponse` 두 개의 DTO를
명시했는데, 실제로는 `TokenResponse` 하나로 통합했다(필드가 완전히 같아서). 이 결정이 코드
주석에는 있지만 기획서(`docs/10.md`)에는 반영되지 않았다.

**왜 고쳐야 하는가**
- `docs/rules/pr-template.md`: "기획서와 실제 구현이 다른 부분이 있다면 반드시 명시"를
  코드 주석만으로 대체한 셈이라, PR 리뷰 시점에 이 차이가 드러나지 않을 위험이 있다.

**해결 방안**
1. **`docs/10.md`를 사후 수정해서 `TokenResponse` 통합을 반영**
   - 장점: 가장 간단, 코드 변경 없음, 기획서가 실제 구현과 다시 일치.
   - 단점: "구현 먼저, 기획 승인은 나중"이 되어 워크플로우 취지와 순서가 엄밀히는 어긋남 —
     다만 필드가 100% 동일한 단순 통합이라 실질 리스크는 낮음.
2. **기획서대로 `LoginResponse`/`ReissueResponse`로 다시 분리**
   - 장점: 기획서와 100% 일치.
   - 단점: 완전히 동일한 필드를 가진 DTO 두 개 — "불필요한 추상화/중복 지양" 원칙과 반대 방향.
3. **지금은 그대로 두고 PR 본문에만 "기획서와 다른 점"으로 명시**
   - 장점: 지금 당장 할 일이 적음.
   - 단점: 기획서 파일 자체는 계속 낡은 상태로 남음.

**결정**: 1번 적용 완료 — `docs/10.md`의 엔드포인트 응답 DTO 표기를 `TokenResponse`로 수정하고,
"리스크 및 고려사항"에 통합 사유를 명시했다. 앞으로 구현이 기획서와 달라지면 **그때그때
바로 기획서를 최신 상태로 갱신한다** (`docs/rules/branch-workflow.md`에 규칙으로 추가함).

## ⚫ 트러블 4 [75] Refresh Token이 userId로만 키잉되어 "멀티 디바이스 = 자동 로그아웃" — ❌ 기각

**문제**
`RedisKeyType.REFRESH_TOKEN`의 key가 `userId` 하나뿐이라, 같은 계정으로 두 번째 기기에서
로그인하면 첫 번째 기기의 Refresh Token이 Redis에서 조용히 덮어써진다. 첫 번째 기기가 나중에
재발급을 시도하면, 실제로는 탈취/재사용이 아닌데도 `INVALID_REFRESH_TOKEN`으로 거부되어
말없이 로그아웃된 것처럼 보인다.

**왜 고쳐야 하는가(혹은 왜 지금은 괜찮은가)**
- 기획서(`docs/10.md`)는 "key: userId"라고만 적었을 뿐, 멀티 디바이스/동시 세션 정책을 전혀
  논의하지 않았다 — 의도된 단일 세션 정책인지, 단순히 누락된 고려사항인지가 불명확하다.
- 실사용자가 폰+PC 등 여러 기기를 쓰는 건 흔한 패턴이라, "말없이 로그아웃됨"은 문의/버그
  리포트로 이어질 가능성이 있다.

**해결 방안**
1. **지금 구조(단일 세션) 유지, 기획서에 "의도된 동작"으로 명시만 하고 넘어간다**
   - 장점: 코드 변경 없음, 구현 단순함 유지.
   - 단점: 실제로 의도한 정책인지 주인의 확인이 필요.
2. **Redis 키를 `userId:deviceId`(또는 세션 UUID)로 바꿔 기기별 다중 세션 지원**
   - 장점: 실제 멀티 디바이스 사용 패턴에 맞음.
   - 단점: 로그인 요청/응답에 deviceId 관리 추가, "이 기기만" vs "전체 기기" 로그아웃 정책까지
     새로 설계해야 함 — 별도 기능/이슈감.
3. **userId당 최대 N개 세션까지 허용 (Redis Set/Hash로 관리)**
   - 장점: 완전한 기기별 관리보다는 단순.
   - 단점: 여전히 추가 설계/구현이 필요해 이번 이슈 범위 밖.

**결정**: 기각 — 현재 서비스 단계에서 멀티 디바이스 로그인은 굳이 필요하지 않다고 판단해
1번(현행 단일 세션 유지)으로 확정. `docs/10.md`에 "의도된 동작"으로 명시 완료. 나중에
멀티 디바이스 요구가 생기면 그때 별도 이슈로 분리해서 2번/3번 방안을 재검토.

## 🟡 트러블 5 [75] 커밋 `e6abc6e`가 `test:` 타입인데 실제로는 리팩터링도 포함

**문제**
커밋 메시지는 `test(auth): 로그인/재발급/로그아웃 테스트코드 추가 및 JWT 빈 등록 방식 수정`으로,
제목의 타입 접두사는 `test`지만 본문에서 밝혔듯 `SecurityConfig`/`JwtProvider` 등 프로덕션
코드의 빈 등록 방식 리팩터링도 같이 묶여 있다.

**왜 고쳐야 하는가**
- `docs/rules/commit-convention.md`: 작은 task 단위로 자주 커밋, 타입이 변경 성격과 일치해야
  함 — `git log --oneline`만 훑는 사람은 이 커밋에서 프로덕션 코드가 바뀐 걸 놓치기 쉽다.

**해결 방안**
1. **그대로 두고 앞으로만 규칙 준수**
   - 장점: 지금 아무 작업도 필요 없음.
   - 단점: 규칙 위반 기록이 이 브랜치 히스토리에 남음.
2. **`git rebase -i`로 해당 커밋을 `refactor(common): ...` + `test(auth): ...` 두 개로 분리**
   - 장점: 히스토리가 깨끗해짐.
   - 단점: 대화형 리베이스(`-i`)는 전역 규칙상 사용 금지 — **이 방법 자체를 실행할 수 없음**.
     이미 그 위에 여러 커밋이 쌓여 있어 충돌 위험도 있음.
3. **커밋 히스토리는 그대로 두고, PR 설명에 "이 커밋은 `test:` 라벨이지만 리팩터링도 포함됨"을
   명시해 리뷰어 컨텍스트만 보강**
   - 장점: 히스토리를 건드리지 않고, 리뷰 시점에 오해를 방지.
   - 단점: 근본적으로 커밋 자체는 안 고쳐짐.

**제안**: 2번은 규칙상 불가하므로 3번(PR 설명에 명시)으로 처리.

## 🟡 트러블 6 [Low/Medium] Refresh Token TTL이 두 곳에 중복 정의됨

**문제**
`RedisKeyType.REFRESH_TOKEN`의 TTL(`Duration.ofDays(14)`, 하드코딩)과
`jwt.refresh-token-expiration`(application.yml, 1209600000ms = 14일)이 같은 값을
의미하지만 별도로 관리된다.
- 위치: `src/main/java/com/remake/gone/common/redis/RedisKeyType.java:20`

**왜 고쳐야 하는가**
- 나중에 둘 중 하나만 바꾸면 JWT 만료 시점과 Redis 저장 기간이 어긋난다.

**해결 방안**
1. **지금처럼 두고, 두 값을 나란히 바꾸라는 주석으로만 안내 (이미 적용됨)**
   - 장점: 구조 변경 없음.
   - 단점: 사람이 실수로 하나만 바꿀 위험은 여전함.
2. **`RedisKeyType.REFRESH_TOKEN`의 TTL을 `JwtProperties`에서 주입받는 구조로 변경**
   - 장점: 단일 진실 공급원(single source of truth)이 됨.
   - 단점: `RedisKeyType`이 지금 순수 enum(설정 주입 없음)인 기존 구조를 깨는 변경 — 다른
     모든 `RedisKeyType` 항목에도 영향 범위가 넓어져 이번 이슈 범위를 넘어섬.

**제안**: 1번(현행 유지) — 이번 범위 밖으로 판단, 필요해지면 별도 리팩터링 이슈로.

## ⚪ 트러블 7 [환경 제약] Redis 연동 실제 환경 미검증

**문제**
로컬 개발 환경에 Redis가 떠 있지 않고(Docker Desktop도 꺼져 있음), 클라이언트 도구도 없어
아래는 Mockito 단위 테스트로만 검증했고 **실제 Redis에 대해서는 확인하지 못함**:
- 로그인 시 Refresh Token이 Redis에 실제로 저장되는지
- 재발급 시 Redis 값이 실제로 교체(rotation)되는지
- 로그아웃 시 Redis에서 실제로 삭제되는지

**검증한 것 (참고)**
- 실제 로컬 MySQL에 Gbsw/User row를 만들어 `AuthService.login()`을 직접 호출 →
  로그인 ID 조회, 비밀번호 검증(BCrypt), JWT 서명까지 정상 동작 확인.
- 비밀번호 오류 시 `INVALID_CREDENTIALS`로 거부되는 것 확인.
- 검증에 사용한 테스트 데이터(Gbsw/User)는 확인 후 삭제 완료.

**해결 방안**
1. **병합 전 로컬에서 Redis를 띄우고 수동 확인** (예: `docker run -p 6379:6379 redis:7`)
   - 장점: 가장 확실.
   - 단점: 자동화 아님, 사람이 직접 해야 함.
2. **CI에 Redis 서비스 컨테이너가 이미 있으니(`build-and-test` job), CI 통과를 신뢰 지표로
   삼고 로컬 수동 확인은 생략**
   - 장점: 이미 있는 인프라 재사용, 추가 작업 없음.
   - 단점: CI의 `contextLoads()`/기존 테스트는 Redis 저장/회전/삭제까지 직접 검증하진 않음
     (Mockito 목킹 테스트 위주) — CI 통과가 "Redis 연동이 실제로 된다"는 증거로는 약함.

**제안**: 1번 — 병합 전 로컬 Redis로 로그인→재발급→로그아웃 전체 흐름 한 번 더 수동 확인 권장.
