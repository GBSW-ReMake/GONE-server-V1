# Notion API 명세서 작성 규칙

대상: Notion "💣 API 명세서" 데이터베이스([branch-workflow.md](./branch-workflow.md) 17단계 —
PR이 `dev`에 머지된 게 확인되면 이번에 추가/변경된 엔드포인트를 여기에 반영한다).

## 필드 작성 규칙
- **엔드포인트**: `{Method} {경로}` (예: `PATCH /api/v1/outings/{code}/approve`)
- **Method / 도메인 / 상태 / 인증 필요**: select/checkbox 필드의 기존 옵션을 그대로 쓴다.
  해당하는 도메인 옵션이 없으면 새로 추가한다(예: "외출").
- **API 코드**: 도메인 접두사 + 순번(예: `OUTING_001`, `OUTING_002`, ...). 이 코드는 앱의
  `ErrorCode` enum 값과는 별개의, 이 문서 안에서만 쓰는 식별 번호다 — 같은 도메인 안에서
  엔드포인트가 실제로 구현/머지된 순서대로(기획 순서가 아니라) 번호를 매긴다.
- **Request / Response**: 실제 예시 값이 아니라 **JSON 형식(필드명 + 타입/설명)만** 적는다.
  ```json
  {
    "outingDate": "string (yyyyMMdd)",
    "timeSlot": "LUNCH | DINNER | CUSTOM"
  }
  ```
  `"outingDate": "20260814"`처럼 실제 값을 넣지 않는다 — 기획서(`docs/domain/{도메인명}/{이슈번호}-...md`)에는
  실제 예시가 있으니 거기서 확인하면 되고, 여기는 스키마 참고용이다.
  - 특이사항(예: "CUSTOM일 때만 필수", "실패 시 재시도 규칙")이 있으면 JSON 블록 다음
    **한 줄을 띄우고** 그 아래에 적는다. JSON 블록 안에 섞어 넣지 않는다.
- **예외/오류 처리 / 비고**: 서술형 문단으로 쓰지 않는다 — 표 칸이 좁아서 문단이 깨진다.
  **번호를 매긴 목록**으로 딱딱 끊어서 정리하고, 각 항목은 `<br>`로 구분한다(이 DB의 기존
  줄바꿈 렌더링 방식). 형식 예:
  ```
  1. 403 OUTING_004 TEACHER_MISMATCH - 호출한 선생님이 담당 선생님이 아님<br>
  2. 409 OUTING_005 ALREADY_PROCESSED - 이미 처리된 외출증<br>
  3. 404 OUTING_006 OUTING_NOT_FOUND - 존재하지 않는 code
  ```

## 반영 시점
- PR이 `dev`에 머지된 걸 확인한 뒤 진행한다(머지 전 상태를 미리 적어두지 않는다).
- 그 PR에서 실제로 추가/변경된 엔드포인트만 다룬다. 과거에 이 규칙이 생기기 전 머지돼
  Notion에 아직 없는 엔드포인트를 발견하면, 임의로 다 채우지 말고 주인에게 먼저 확인한다.
