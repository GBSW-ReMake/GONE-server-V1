# Flyway 마이그레이션 버전 규칙

## 새 마이그레이션 = 타임스탬프 버전
새로 추가하는 마이그레이션은 순번(`V1`, `V2`, ...) 대신 타임스탬프 버전을 쓴다.

```
V{yyyyMMddHHmmss}__{설명}.sql
```

예: `V20260824151700__add_outing_ping_location.sql`

- 타임스탬프는 KST 기준 "지금" 값을 그대로 쓴다(별도 변환 불필요). `date +%Y%m%d%H%M%S`
  (또는 동일한 값을 주는 아무 방법)로 얻는다.
- 브랜치 생성 시점에 미리 번호를 확정하지 않는다 — 실제로 마이그레이션 파일을 커밋하는
  순간의 타임스탬프를 쓴다.

## 왜 순번을 버리는가
여러 브랜치가 동시에 진행되는 협업 환경에서 "다음 빈 번호"를 각자 브랜치 기준으로
판단하는 순번 방식은, 병합 순서가 브랜치 생성 순서와 다르면 버전이 겹친다 — 실제로
`dev`에 먼저 병합된 #94가 `V16`을 쓰는 동안 그보다 먼저 분기된 #43도 같은 `V16`을 써서
CI에서 Flyway가 컨텍스트 로딩 자체를 실패시켰다(outing과 무관한 다른 도메인 테스트까지
연쇄 실패, #105). 타임스탬프 버전은 Flyway가 팀 개발용으로 공식 권장하는 방식이고,
같은 초에 두 마이그레이션이 동시에 커밋되는 경우가 아니면 충돌 가능성이 사실상 없다.

## 기존 V1~V17은 그대로 둔다
이미 각 환경(로컬/CI/staging)에 적용된 이력이 있는 `V1`~`V17`(순번 방식)은 재번호하지
않는다 — 되돌리면 각 환경의 `flyway_schema_history`와 어긋나 더 큰 문제가 된다.

Flyway는 버전을 점(`.`)/밑줄(`_`)로 나눠 숫자로 비교하므로, 순번(예: `17`)과 타임스탬프
(예: `20260824151700`)가 섞여 있어도 항상 타임스탬프 쪽이 더 큰 값으로 정렬된다 — 순번과
타임스탬프 버전이 같은 폴더에 섞여 있어도 문제없이 공존한다.
