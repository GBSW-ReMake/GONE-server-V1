# 기능 구현 워크플로우 (v2)

보스가 "이 기능을 구현해줘"라고 요청하면 아래 순서를 반드시 지킨다.
순서를 건너뛰거나 임의로 합치지 않는다. 각 단계 사이의 승인/보고 지점에서는 보스의 확인 없이 다음 단계로 넘어가지 않는다.

> **v2 변경 요약**: (1) 진행 상태를 GitHub 이슈 체크리스트로 외부화, (2) 8단계 "기획서 즉시 수정" 규칙을 설계 변경 여부로 분리해 승인 게이트 우회를 막음, (3) 9단계 리뷰 에이전트의 컨텍스트 격리 명시, (4) 10단계에 CI 통과 확인 추가, (5) Postman(15)을 QA(10) 직후로 재배치하고 PR 리뷰로 인한 계약 변경 시 재확인 규칙 추가, Notion(17)은 머지 후 유지.

## 🚨 한 번에 하나의 기능만 + 📋 진행 상태 추적
- **항상 "이슈 1개 ↔ 브랜치 1개 ↔ 기능 1개"만 동시에 진행한다.** 진행 중인 이슈가 있으면
  새 이슈의 기획서 작성/브랜치 생성/구현을 시작하지 않는다.
- **진행 상태는 모델의 기억이 아니라 레포 상태(이슈의 0~17단계 체크박스)로 관리한다.**
  세션이 끊겨도 이 체크박스를 읽어서 이어간다.
- 상세 규칙(백로그 이슈 생성 기준, QA 중 발견한 버그 처리, 0단계에서 직전 이슈의 15/17단계
  확인 등): [progress-tracking.md](./progress-tracking.md)

## 🚫 dev 직접 푸시 금지
- **`dev`에는 어떤 커밋도 직접 push하지 않는다. 항상 브랜치를 분기해 PR로 머지한다.**
  `dev`는 로컬 feature 브랜치들이 모이는 통합 지점이다(#77 이후 배포 파이프라인은 붙어있지
  않다 — 실제 배포 트리거는 아래 `staging`). 직접 push를 금지하는 이유는 배포 차단이
  아니라 **히스토리/리뷰 규율 유지**다 — 코드 변경이든 문서(기획서)뿐인 변경이든 예외 없이
  PR을 거쳐야 리뷰·커밋 히스토리가 남는다.
- **기획서(2단계)도 예외가 아니다.** "문서만 바뀌니 리뷰가 필요 없다"고 임의로 판단해
  `dev`에 직접 커밋하지 않는다 — 기획서 커밋은 7단계에서 만드는 기능 브랜치의 첫 커밋으로
  넣거나, 별도 `docs/#{이슈번호}-...` 브랜치를 분기해 PR로 머지한다.
- 이미 승인된 기획서를 다듬는 것처럼 사소해 보이는 변경도 동일하게 브랜치+PR을 거친다.

## 🚫 staging 직접 푸시 금지
- **`staging`에는 어떤 커밋도 직접 push하지 않는다.** `staging`에는 CI/CD(#51, #77 —
  push 시 자동 빌드/배포)가 붙어있어, 직접 push하면 그 즉시 실제 배포 파이프라인이
  돈다. `staging`은 오직 `dev` → `staging` **승격 PR**을 통해서만 갱신한다(위
  progress-tracking.md의 "한 번에 하나의 기능만" 절 참고 — 승격 PR은 이미 `dev`에서
  검증된 커밋을 옮기는 것뿐이라 별도 이슈/기획서 없이 진행 가능하다).

## 0. 사전 준비 — 기존 코드 읽기
- 관련 도메인 패키지(`auth`, `user`, `gbsw`, `file` 등)의 기존 controller/service/dto/exception을 먼저 읽고 컨벤션을 파악한다.
    - 공통 응답 포맷: `common/response`
    - 공통 예외 처리: `common/exception` (`CustomException` + `ErrorCode`)
    - Redis 사용 패턴: `common/redis` (`RedisRepository`, `RedisKeyType`)
- 유사 기능이 이미 구현되어 있으면 그 구조를 최대한 재사용한다. 새 패턴을 임의로 만들지 않는다.
- 직전 이슈의 15/17단계 완료 여부를 확인한다 (위 "진행 상태 추적" 참고).

## 1. 이슈 생성
- `.github/ISSUE_TEMPLATE/feature.md` 또는 `bug.md` 기반으로 생성.
- 이슈 본문에 0~17단계 체크리스트를 포함시킨다.
- 상세 규칙: [issue-template.md](./issue-template.md)

## 2. 기획서 생성 (`docs/domain/{도메인명}/{이슈번호}-{도메인명}-{간략한 제목}.md`)
- 엔드포인트를 설계하기 전 [api-design.md](./api-design.md)의 6원칙(단일 책임/빠른 시작/
  일관성/의미 있는 오류/확장성·성능/하위 호환성)을 검토하고, 기획서의 "리스크 및 고려사항"
  절에 해당 원칙과 관련된 판단(예: 페이지네이션 여부, 하위 호환 여부)을 남긴다.
- 기획서 본문 문장은 [sentence-refinement.md](./sentence-refinement.md)의 원칙 1~5를
  따른다(주어를 분명히, 필요한 정보만, 구체적으로, 자연스러운 한국어, 일관된 용어).
- **경로/문서명 규칙**: `docs/domain/{도메인명}/` 폴더 아래에 둔다. 도메인명은 `auth`/
  `user`/`outing`/`neis` 등 커밋 스코프와 동일한 규칙을 따른다(GitHub 이슈에 `domain:X`
  라벨이 있으면 그 값을 소문자로, 없으면 이슈 종류 라벨을 그대로 폴더명으로 쓴다 — 예:
  `chore`/`bug`). 해당 도메인 폴더가 아직 없으면 새로 만든다.
  - 문서명 예: `docs/domain/outing/41-outing-query.md`. 폴더로 도메인이 이미 구분되지만,
    파일명에도 도메인명을 유지한다(검색 결과·링크만 봐도 어떤 문서인지 알 수 있게).
  - 같은 이슈에서 파생되는 QA 문서/부가 문서는 이 base 이름 뒤에 접미사를 붙인다
    (`{base}-QA.md`, `{base}-api-spec.md` 등), 같은 폴더에 둔다.
  - 그 도메인 전체를 다루는 마스터 기획서(예: `outing-domain.md`)가 있으면 파일명 맨 앞에
    `1_`을 붙여(`1_outing-domain.md`) 폴더 안에서 항상 맨 위로 정렬되게 한다.
- 이슈 1개당 엔드포인트 1~2개, 또는 기존 서비스 로직 수정 1건으로 범위를 좁힌다. 범위가 넘치면 이슈를 분리한다.
- 엔드포인트 중심 양식:
    - 개요/목적, 관련 이슈 링크
    - 엔드포인트별: `Method + Path`, 요청 DTO, 응답 DTO, 성공/에러 상태코드 및 `ErrorCode`, 인증/권한 요구사항
    - 기존 로직을 수정하는 경우: 변경 전/후 동작 차이
    - 데이터 모델 변경: 엔티티 필드 추가/변경, Flyway 마이그레이션 필요 여부(파일명 버전
      형식은 [migration-convention.md](./migration-convention.md) 참고)
    - 영향 받는 기존 코드/테스트
    - 리스크 및 고려사항

## 3. 기획서 검토 요청
- 기획서 작성 후 반드시 보스에게 검토를 요청한다. 보스가 검토하기 전에는 절대 먼저 작성/구현을 진행하지 않는다.

## 4. 검토 받기
- 보스의 피드백을 기다린다.

## 5. 수정
- 검토 중 지적된 사항은 기획서에 즉시 반영하고 재검토를 요청한다.

## 6. 검토 종료
- 보스의 명시적 승인이 있어야 다음 단계(브랜치 생성)로 진행한다.

## 7. 브랜치 생성
- `dev`에서 분기.
- 네이밍: `feat/#{이슈번호}-{짧은-영문-slug}` (버그 수정은 `fix/#{이슈번호}-...`)

## 8. 기능 구현
- 기획서에 정의된 범위를 벗어나지 않는다 (스코프 크립 금지). 범위 밖의 리팩터링/개선은 별도 이슈로 분리 제안한다.
- 작은 task 단위로 커밋한다 (예: 엔티티/마이그레이션 → 서비스 로직 → 컨트롤러 → 테스트 순서로 분리 커밋).
- 커밋 규칙: [commit-convention.md](./commit-convention.md)
- 코드 스타일: [code-style.md](./code-style.md)
- 코드 내 주석(Javadoc/인라인)의 문장 구조: [sentence-refinement.md](./sentence-refinement.md)
  (원칙 1~6, 특히 원칙 6 "코드 주석 전용 규칙")
- 테스트: [test-convention.md](./test-convention.md)
- **기획서와 실제 코드가 달라지는 경우, 변경의 성격에 따라 다르게 처리한다:**
    - **구현 세부사항 변경** (DTO 필드 통합/분리, 내부 메서드 시그니처, 변수명 등 — 승인받은
      엔드포인트 계약·정책에 영향 없음): 그 즉시 기획서 파일을 수정해 실제 구현과 일치시키고
      계속 진행한다. PR 설명에만 적어두고 넘어가지 않는다.
    - **설계/정책 변경** (엔드포인트 경로/메서드, 요청·응답 스키마, 인증 요구사항, 에러코드
      정책 등 승인받은 계약 자체가 바뀌는 경우): **구현을 중단하고 4단계(검토 받기)로 되돌아가
      재승인을 받는다.** 승인된 기획서를 임의로 사후 수정해서 넘어가지 않는다 — 이건 3~6단계
      승인 게이트를 무력화하는 것과 같다.
    - 애매하면 설계/정책 변경 쪽으로 간주하고 재승인을 요청한다.

## 9. 코드 리뷰 (자체 점검)
- 기능 구현이 끝나면 QA 전에 diff를 리뷰한다. **직접 리뷰하지 않고, 컨텍스트가 격리된 별도
  에이전트에게 `code-review` 스킬로 리뷰를 맡긴다.** 결과는 QA(10단계)와 합치지 않고
  `docs/domain/{도메인명}/{이슈번호}-{도메인명}-{간략한 제목}-code-review.md`로 즉시
  문서화한다.
- 에이전트를 어떻게 격리하는지, 결과를 어떤 형식으로 남기는지는
  [code-review-isolation.md](./code-review-isolation.md) +
  [code-review-template.md](./code-review-template.md) 참고.

## 10. 기능 구현 종료 → QA/QC
- `./gradlew build`, `./gradlew test`, `./gradlew checkstyleMain` 로컬 통과를 확인한다.
- **GitHub Actions CI 파이프라인도 통과했는지 확인한다.** 로컬 통과와 CI 통과는 다를 수 있다
  (예: `contextLoads()`처럼 CI에서만 필요한 서비스 컨테이너 의존성). 로컬 통과만으로 이 단계를
  끝내지 않는다.
- 기획서에 정의된 엔드포인트별 정상/에러 케이스를 직접 검증한다(가능하면 실제 서버 기동 후 확인).
- 이 검증에 사용한 요청들을 바탕으로 15단계(Postman) 작업을 이어서 진행한다.

## 11. 문제사항 보고
- QA(10단계)에서 발견된 문제를 심각도별로 정리해
  `docs/domain/{도메인명}/{이슈번호}-{도메인명}-{간략한 제목}-QA.md` 파일로 문서화한 후
  보고한다(코드 리뷰 결과는 9단계에서 이미 별도 파일로 작성했으므로 여기서는 QA 결과만
  다룬다 — 보고 시에는 두 파일을 같이 언급한다). 임의로 판단해 누락하지 않는다.
    - **Critical**: 데이터 유실, 보안/인증 우회
    - **High**: 핵심 플로우 실패
    - **Medium**: 예외 케이스 미처리, 환경 제약으로 검증 못 한 항목
    - **Low**: 사소한 개선점

## 12. 검토
- 정리한 보고 내용을 바탕으로 보스에게 검토를 요청한다.

## 13. 수정 반영
- 보스가 수정을 요청하면 반영하고, 요청이 없으면 다음 단계로 넘어간다.
- 이 수정이 엔드포인트 계약을 바꾸는 경우, 8단계의 "설계/정책 변경" 규칙에 따라 15단계에서
  만든 Postman 컬렉션도 함께 갱신한다.

## 14. 작업 완료 보고
- 변경 사항 요약, 테스트 결과, 남은 이슈(있다면)를 간결하게 보고한다.

## 15. Postman 컬렉션 정리
- **10단계 QA에서 실제 서버로 검증한 요청들을 바탕으로, PR 생성 전에** 이번에 추가/변경된
  엔드포인트를 Postman 컬렉션에 반영한다. QA 때 이미 만든 요청을 재사용하면 되므로 별도
  작업이 아니라 QA의 연장선으로 처리한다.
- 컬렉션 안을 어떻게 구조화하는지(최상위 엔드포인트 목록, 사전 준비/에러 케이스 폴더,
  기능별 검증 폴더 등)는 [postman-collection-structure.md](./postman-collection-structure.md)
  참고.
- 워크스페이스/API 키 위치, 푸시 방법은 리포지토리의 `postman/` 폴더와 `.env`
  (`POSTMAN_API_KEY`, `POSTMAN_WORKSPACE_ID`)를 따른다.
- **PR 리뷰(16단계 이후 실제 GitHub 코드 리뷰)로 엔드포인트 계약이 바뀌면, 머지 직전에
  Postman 컬렉션이 최종 계약과 일치하는지 다시 확인한다.** 어긋나 있으면 머지 전에 갱신한다.

## 16. PR 생성
- 보고 후 보스의 확인 절차를 거친 뒤에만 PR을 생성한다.
- 상세 규칙: [pr-template.md](./pr-template.md)
- PR이 `dev`에 머지되면, `closes #N`은 자동 종료되지 않으므로 관련 이슈를 직접
  `gh issue close`로 닫는다 ([pr-template.md](./pr-template.md) 참고).
- 머지 전, 팀원 리뷰로 계약이 바뀌었다면 15단계 재확인을 완료했는지 확인한다.

## 17. Notion API 명세서 갱신
- PR이 `dev`에 머지된 게 확인되면(보스가 "머지했어"라고 알려주거나 직접 확인), 이번에
  추가/변경된 엔드포인트를 Notion API 명세서에 반영한다.
- **이 단계를 머지 후에 두는 이유**: Notion은 팀 전체가 참조하는 확정 스펙이다. PR 리뷰로
  계약이 바뀔 가능성이 남아있는 동안 미리 반영하면, 팀원이 아직 확정되지 않은 스펙을 보고
  작업할 위험이 있다. 반면 Postman(15단계)은 개발자 본인의 테스트 도구이므로 QA 시점에
  바로 반영하는 게 맞다 — 이게 두 문서의 반영 시점이 다른 이유다.
- 작성 형식(필드별 규칙, JSON 스키마만 적기, 예외/비고 번호 목록 등)은
  [notion-api-spec.md](./notion-api-spec.md)를 따른다.
- 기획서(`docs/domain/{도메인명}/{이슈번호}-...md`)에 이미 있는 요청/응답 예시, 에러 코드
